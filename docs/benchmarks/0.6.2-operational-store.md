# 0.6.2 Operational Store Benchmarks

Measured on the local API-source database on 2026-07-31. These figures are kept
separate because steady-state growth, a reversible migration, and final cleanup
answer different operational questions.

## Summary

| Figure | Measurement | Meaning |
|---|---:|---|
| Pre-migration database | 145,592,320 bytes | Existing `0.6.1` database |
| Side-by-side migration database | 161,120,256 bytes | Temporary fixed + legacy tables for rollback |
| Migration disk increase | 15,527,936 bytes (10.67%) | Temporary safety cost through `0.6.6` |
| Live migration time | 7.204 seconds | Copy, verify, audit, and cut over 18,436 rows |
| Streamed migration working-set increase | 17,408,000 bytes | Instrumented rehearsal peak above baseline |
| Projected post-cleanup database | 83,251,200 bytes | Legacy table dropped and SQLite vacuumed on a copy |
| Projected saving from pre-migration | 62,341,120 bytes (42.82%) | Eventual durable disk reduction |
| Marginal API snapshot date | 716,800 bytes for 838 sensors | Real-data daily facts, ledger, coverage, and revision growth |
| Marginal bytes per sensor-date | 855.37 bytes | Realistic steady-state planning figure |

The 716,800-byte daily figure excludes growth in shared reference tables and
brand-new variable event payloads. Those do not scale one-for-one with every sensor
date, so combining them would obscure the stable daily-fact cost.

## Migration Memory

The first all-at-once migration rehearsal increased the working set by 218,836,992
bytes. Streaming one date at a time reduced the measured increase to 17,408,000
bytes, a 92.0% reduction. The instrumented streamed rehearsal took 12.972 seconds;
instrumentation and copied-database I/O make it deliberately more conservative than
the 7.204-second live run.

## Small Mock Control

A fresh three-date mock run confirmed the no-artifact path and provided a lower
bound for small installations:

| Date step | SQLite growth | Time | Peak Python allocation |
|---|---:|---:|---:|
| First date, 9 sensors | 4,096 bytes | 85.43 ms | 1,285,472 bytes |
| Second date | 12,288 bytes | 223.86 ms | 1,272,294 bytes |
| Third date | 8,192 bytes | 329.30 ms | 1,275,740 bytes |

The average after the first date was 10,240 bytes per mock date. No processed
snapshot, trend, reference, model, or metadata artifact file was created by the
routine flow.

## Read Checks After Cutover

Local FastAPI `TestClient` checks against the migrated API database:

| Route | Status | Response bytes | Time |
|---|---:|---:|---:|
| Artifact inventory | 200 | 60,800 | 68.87 ms |
| Full equipment tree | 200 | 578,070 | 51.42 ms |
| Latest snapshot (`2026-07-27`) | 200 | 1,868,037 | 35.55 ms |
| Full-range trends | 200 | 341,923 | 68.03 ms |

These are local application timings, not network latency or a formal load test.
They verify that the live fixed-table cutover stayed inside the existing response
path and did not require file fallback.

The final project suite completed with 137 passing tests and one skipped live-canary
test in 66.43 seconds.
