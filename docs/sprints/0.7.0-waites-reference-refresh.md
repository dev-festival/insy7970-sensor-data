# Sprint 0.7.0 - Waites Reference Refresh

Status: Planned.

## Problem Statement

The durable Waites asset-tree, equipment, and installation-point reference tables
are refreshed only when a daily synchronization needs to acquire sensor facts. An
already verified date is intentionally reused without calling Waites. Consequently,
an operator cannot promptly reflect an asset-tree move, renamed equipment, or
installation-point change without coupling that reference update to an unrelated
daily refetch/rebuild.

The service needs one explicit, bounded administration operation that refreshes
current Waites navigation references without acquiring readings, changing daily
facts, rebuilding models, or advancing synchronization state.

## Working Decisions

### `sync --tree` is a reference-only operation

Add the operator command:

```powershell
uv run sensor-data sync --tree
uv run sensor-data sync --tree --json
```

`--tree` fetches the configured facility's `asset-tree`, `equipment`, and
`installation-points` endpoints, validates their reference shapes, and upserts the
three durable reference tables. It is not a date synchronization mode and does not
fetch readings or action items.

The name `--tree` is intentionally user-facing shorthand: the refreshed navigation
tree includes asset-tree hierarchy, equipment names and membership, and
installation-point/sensor membership. A later alias may be added only when it does
not broaden the operation or make the CLI less discoverable.

### Reference refresh is separate from daily raw runs

Daily raw captures are complete, date-scoped evidence bundles. They must not contain
a partial three-endpoint capture. The refresh uses its own bounded reference-capture
record, separate from `raw/waites/date=YYYY-MM-DD/`, so daily validation and
retention contracts remain valid.

Capture metadata must record the configured source and facility, timestamp,
endpoint names, response counts, validation outcome, and secret-safe request
parameters/checksums. The existing administration audit records the operation and
its final status. Reference refresh must use the configured raw-retention policy or
an equally bounded lifecycle; it must not create an unbounded second reference
mirror.

### Current references are authoritative for navigation

The refresh upserts the existing reference identity keys:

- `asset_tree_id` for hierarchy, name, facility, parent, and path;
- `equipment_id` for name, tree membership, facility, and customer asset;
- `installation_point_id` for name, equipment/sensor membership, and installation
  metadata.

It does not rewrite historical daily snapshot labels or infer deletions from an
omitted provider row. The existing read paths continue to compose current reference
labels with date-bounded activity facts.

### It shares normal administrative safeguards

The operation uses the existing configured source/data directory, Waites credential
handling, single-writer lease, concise failures, and `--json` result conventions.
It does not require `INSY_SYNC_START_DATE` and does not read or change the durable
synchronization cursor, per-date ingestion state, model readiness, or retention for
daily facts.

`--tree` is mutually exclusive with `--date`, `--start-date`, `--end-date`,
`--max-days`, and `--defer-models`. `--env-file` and `--json` remain available.

## Requirements

1. Add `sensor-data sync --tree` with human-readable and machine-readable results.
2. Fetch only Waites `asset-tree`, `equipment`, and `installation-points` endpoints
   for the configured facility.
3. Validate reference payloads before changing durable reference rows; an invalid or
   failed endpoint must leave the durable references unchanged.
4. Upsert all three existing durable reference tables atomically, preserving their
   first/last-loaded metadata and existing identity contracts.
5. Record a bounded, secret-safe reference-capture provenance record and an
   administration audit outcome without adding a parallel processed reference
   export.
6. Reuse the writer lease and return a clear busy/failure result without partial
   persistence when another `sync` or `rebuild` writer owns the store.
7. Keep ordinary `sync` behavior unchanged: it continues to refresh references when
   it acquires a new daily source date, while an already-current bare invocation
   remains a non-mutating no-op.
8. Update CLI/operator documentation and help text with the reference-refresh
   command, its scope, and its mutual exclusions.

## In Scope

- One `sync --tree` flag and its reference-only service path.
- Waites API and mock-fixture support for the three reference endpoints.
- Atomic durable reference upserts, bounded provenance, audit summaries, and tests.
- CLI and operations documentation.

## Out of Scope

- Reading, rebuilding, or re-fetching daily sensor facts, action items, or models.
- A browser control for editing or refreshing references.
- Provider-side mutation, manual reference editing, or deletion/tombstone policy.
- A new top-level command or an additional processed reference-file mirror.
- Changes to synchronization cursor semantics, scheduled-sync behavior, or raw
  evidence retention for daily data.

## Compatibility Gate

The existing five-command top-level CLI remains unchanged. `--tree` is an option of
`sync`, not a sixth command. Existing daily `sync`, `rebuild`, `doctor`, web
navigation, exports, and date-bounded activity behavior must retain their current
contracts.

## Acceptance Criteria

1. `uv run sensor-data sync --tree` calls exactly the three reference endpoints and
   returns their counts and a secret-safe capture/audit summary.
2. `uv run sensor-data sync --tree --json` returns a stable result that distinguishes
   successful refresh, validation/source failure, and writer contention.
3. A successful refresh updates current asset-tree and equipment names/membership
   visible through the existing equipment-tree read path without adding daily facts
   or model rows.
4. The synchronization cursor, per-date ingestion records, snapshot revisions, and
   daily raw run directories are unchanged by a reference-only refresh.
5. An invalid payload or failed endpoint leaves all three durable reference tables
   unchanged.
6. A concurrent `sync`/`rebuild` operation is rejected before provider work or
   durable-reference writes occur.
7. `--tree` combined with any date/planning/model option fails with concise usage
   guidance.
8. Bare `sync` remains a successful non-mutating no-op when the service is current.

## Test Out Plan

- Add CLI help, option-conflict, human-readable, and `--json` contract tests.
- Use a fake Waites client to prove the reference refresh requests only the three
  reference endpoints and never reading/action-item endpoints.
- Verify atomic upsert updates names, hierarchy, equipment membership, and
  installation-point membership through the existing SQLite/read-service contracts.
- Verify failed validation or provider errors preserve prior durable references.
- Verify cursor, daily ingestion/model facts, and daily raw directories are
  unchanged by the refresh.
- Verify writer-lease contention and mock/API configuration failures are concise and
  do not expose credentials.
- Run `uv run pytest` and update any affected CLI documentation examples.

## Next Sprint Lead In

This sprint deliberately supplies only on-demand reference freshness. Any policy
for provider deletions, history of reference changes, scheduled reference-only
refreshes, or browser administration should be proposed separately after operators
have used the bounded command.
