# Sprint 0.5.1 - Snapshot Trend Debugging

## Problem Statement

The Snapshot Trend panel currently reports the number of scoped daily sensor rows,
not the number of usable readings for the selected metric and dimension. Sparse data
can therefore look like a complete trend. The custom chart renderer also removes null
points before constructing its categorical date axis, which can place dates out of
order and make continuous lines misleading.

Snapshot details have a second source of confusion: the selected Snapshot date is
hidden in Snapshot mode. Changing the global Start or End date does not necessarily
update that hidden date, so the Measurements table can describe a different day from
the visible range end.

This sprint makes sparse-data representation trustworthy and inspectable without
changing Waites ingestion or treating missing readings as an upstream failure.

## Working Decisions

### Date interaction

The Trend panel is the Snapshot-date picker.

- Clicking a plotted trend point selects that point's calendar date as the Snapshot
  date and refreshes the full Snapshot review for the existing source, scope, and
  date range.
- The Measurements table therefore shows all scoped sensors for the clicked date,
  not only the sensor whose point was clicked.
- The selected Snapshot date is displayed in the pinned Snapshot context. It is not
  a hidden state.
- On initial load and whenever Start or End changes, the Snapshot date defaults to
  the selected range End. It must always be inside the inclusive selected range.
- The Trend range remains unchanged when a point is clicked. Cluster context, events,
  and measurements continue to use the same Snapshot date, as they do today.

### Chronological, continuous trend lines

Trend dates use a real calendar/time axis spanning the selected inclusive range. The
axis is ordered chronologically and includes the range even when a sensor has no
value on a date.

Lines stay continuous across unavailable daily readings. They must not imply that a
value was observed on every day, however:

- actual readings render as visible dots;
- a connection that crosses one or more unavailable daily readings renders as a
  lighter, dashed monotone spline;
- a connection between adjacent observed dates renders as a solid monotone spline;
- the curve must be monotone in time and must not overshoot observed values.

This preserves the requested continuous visual flow while making missing intervals
visibly distinct from observed day-to-day movement. The renderer must not interpolate,
backfill, or create synthetic values in the response or in the measurement table.

### Coverage is a data-availability signal

Coverage applies to the selected trend value field, such as
`rms_vel_mean_y`; it is not an equipment-health status.

```text
expected values = scoped daily sensor rows in the selected range
observed values = expected rows with a finite selected-field value
coverage percent = observed values / expected values * 100
```

The Snapshot Metric control bar displays the selected metric, dimension where
applicable, and overall coverage percentage. Its coverage badge uses both text and
color:

| Coverage | Display state |
|---|---|
| 80-100% | green / good availability |
| 50-79% | amber / partial availability |
| below 50% | red / sparse availability |

For example, the A104547 RMS Velocity Y range from 2026-07-06 through 2026-07-25
has 18 observed values from 60 expected values: `30% coverage`.

### Measurement and diagnostic details

Measurements remain a one-day Snapshot table. Its header explicitly includes the
selected Snapshot date and labels its count as the number of sensors/measurement rows
for that date, not a trend-range summary. Missing selected-field values render as
`No data` rather than an ambiguous empty cell.

Immediately below Measurements, add a Snapshot Diagnostics table for the selected
metric and dimension:

```text
Sensor | Observed days | Expected days | Coverage | Missing dates
```

One row appears for each scoped sensor. `Missing dates` is a chronological,
human-readable list for the selected field; it is an availability description, not an
error message or a claim of sensor failure.

## API / Data Contract

`GET /api/snapshot-review/{snapshot_date}` remains the browser's single Snapshot
request. Its `trend` object adds field-specific coverage while retaining `row_count`
for backwards compatibility:

```json
{
  "value_field": "rms_vel_mean_y",
  "row_count": 60,
  "coverage": {
    "expected_value_count": 60,
    "observed_value_count": 18,
    "coverage_percent": 30.0,
    "sensors": [
      {
        "installation_point_id": "116954",
        "sensor_name": "Motor - DE",
        "expected_value_count": 20,
        "observed_value_count": 5,
        "coverage_percent": 25.0,
        "missing_dates": ["2026-07-07"]
      }
    ]
  }
}
```

The response must keep the existing complete `sensor_rows`, including null values for
unavailable selected fields. Browser rendering is responsible for creating visual
segments; it must not receive or manufacture interpolated numeric values.

## Requirements

1. Normalize Snapshot date whenever the global source or date range changes; prevent
   an out-of-range Snapshot request.
2. Show the active Snapshot date in the pinned Snapshot context.
3. Make plotted trend points keyboard accessible and clickable. Activating a point
   updates the Snapshot date and reloads the Snapshot review.
4. Render ISO snapshot dates on a chronological calendar axis, never in trace or
   sensor discovery order.
5. Render monotone spline segments with the solid/dashed availability treatment
   described above, retaining visible dots for real readings.
6. Compute overall and per-sensor coverage from finite values of the selected trend
   field, including zero as an observed value.
7. Add the accessible, color-coded coverage badge to the Snapshot Metric control
   bar.
8. Label Measurement rows with their Snapshot date and render unavailable selected
   values as `No data`.
9. Add the per-sensor Snapshot Diagnostics table directly below Measurements.
10. Preserve all existing scope rules, Maximo activation boundaries, and read-only
    API behavior.

## In Scope

- Snapshot date normalization, visible context, and plot-point selection.
- Snapshot trend coverage calculations and response fields.
- Chronological time-axis and continuous spline rendering.
- Missing-interval visual treatment.
- Coverage badge and diagnostic table.
- Tests for sparse metric data, point-date selection, date-range changes, and
  chronological rendering.

## Out of Scope

- Changes to Waites API retrieval, validation, raw-retention policy, or SQLite
  ingestion.
- Declaring missing data a sensor, equipment, or communications fault.
- Numeric interpolation, backfilling, or forecasting.
- New trend endpoints or a second browser request for Snapshot diagnostics.
- Changes to Maximo work-order querying or Events activation rules.
- User-configurable coverage thresholds.

## Acceptance Criteria

1. A point clicked on 2026-07-20 changes the Snapshot context and Measurements table
   to 2026-07-20 for the current scope.
2. Changing the range End to 2026-07-25 resets an existing Snapshot date outside the
   range to 2026-07-25.
3. A selected 2026-07-06 through 2026-07-25 range appears left-to-right in calendar
   order for every trend trace, regardless of which sensor provides the first value
   on a date.
4. For A104547 RMS Velocity Y, the Snapshot Metric control displays 30% coverage and
   the diagnostic rows report 5/20, 7/20, and 6/20 observations for Motor-DE,
   Gearbox-DE, and Gearbox-NDE respectively.
5. The renderer shows points on their actual dates and uses a visibly distinct but
   continuous connection over unavailable dates.
6. The Measurements header makes its selected Snapshot date clear; no snapshot date
   outside the visible range can be displayed.
7. Existing Snapshot, Trend, Cluster, Drift, and Maximo Events behavior remains
   available with no JavaScript errors.
