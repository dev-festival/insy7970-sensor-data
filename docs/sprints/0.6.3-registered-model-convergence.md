# Sprint 0.6.3 - Registered Model Convergence

**Status:** Complete on 2026-07-31. The active policy is live across the current
API range; retained legacy rows remain available for rollback through `0.6.6`.

## Problem Statement

Sprint `0.6.2` moved daily facts into a fixed SQLite schema and also advanced the
registered clustering path: it now builds feature rows from SQLite snapshots,
persists registered model and drift results in SQLite, and creates no routine
feature/model/drift file mirrors.

The remaining problem is convergence, not another storage migration. Two clustering
families still exist:

- legacy dimension-oriented feature, cluster, pair-drift, alignment, and
  cluster-window file orchestration;
- the registered feature-space model and drift tables used by the current browser.

The registered implementation still imports private mathematical helpers from the
legacy artifact implementation. Its policy is not service-owned: the browser and
API can request arbitrary feature-space and `k` combinations that may not exist.
Completed runs can be reused without proving that their input snapshot revision is
still current. A single missing or stale date can also cause an entire Drift window
to fail even when other adjacent pairs are complete.

This sprint creates one operational model engine and one versioned active policy.
It makes readiness follow the durable snapshot revision, returns useful partial
Drift windows, and removes legacy clustering loaders from FastAPI.

## Baseline Inherited from 0.6.2

The following are existing guarantees to preserve and test, not new implementation
work for this sprint:

- Fixed `sensor_daily_facts` rows are the model input authority.
- Registered feature vectors are constructed from SQLite rows in memory.
- Registered model runs, assignments, centroids, PCA coordinates, drift rows, and
  centroid alignment are persisted in SQLite.
- Normal registered builds create no feature, cluster-model, or
  cluster-model-drift artifact directories.
- Snapshot revisions exist and can anchor derived-model freshness.

Historical feature/model files and the legacy clustering code remain available for
parity checks and rollback until sprint `0.6.6`; they are not operational authority.

## Working Decisions

### One active model policy

The service owns the active model configuration:

- supported feature-space definitions and metric/dimension mapping;
- active `k`;
- algorithm and random seed;
- feature policy version;
- scaling policy;
- convergence settings that can affect deterministic results.

These values produce one model-policy version. This means one sanctioned recipe,
not one database row: the recipe is applied per source/date and supported feature
space. The browser does not choose arbitrary `k` values or request unbuilt model
variants.

### One reusable mathematical engine

Scaling, KMeans, PCA, quality metrics, and centroid alignment live in a small engine
that has no file or CLI orchestration responsibilities. The registered pipeline is
the only operational caller. Explicit legacy commands may temporarily reuse the
engine, but FastAPI does not retain a second clustering implementation.

### SQLite remains the direct input and output boundary

The model engine receives feature rows derived from fixed daily facts and returns
computed results for transactional SQLite persistence. Feature and model files are
neither inputs nor coordination state. This preserves the `0.6.2` path rather than
rebuilding it.

### Readiness follows snapshot revision and policy version

A model is `ready` only when both its input snapshot revision and model-policy
version match the current values. A completed but mismatched model is `stale`, not
ready. Rebuilding a snapshot invalidates only that date's dependent model results
and drift pairs touching that date.

### Gaps are data, not total failure

Drift over a range returns every complete adjacent pair plus explicit diagnostics
for missing or stale models/pairs. A first, middle, or last gap does not discard
valid results elsewhere in the requested range.

## Requirements

1. Extract scaling, KMeans, PCA, metric, and centroid-alignment math from legacy
   artifact orchestration into a deterministic, storage-independent engine.
2. Define one typed active model policy in application configuration/code,
   including feature mapping, `k`, algorithm, seed, scaling, and convergence values.
3. Derive a stable model-policy version from every setting that can change model
   output.
4. Preserve direct fixed-SQLite-to-feature computation and prohibit feature or
   snapshot CSV dependencies in the registered path.
5. Persist each model's exact input snapshot revision and model-policy version with
   its run, assignments, centroids, PCA coordinates, metrics, and warnings.
6. Persist each model and drift result transactionally so a failed build cannot be
   exposed as ready.
7. Define one readiness predicate that reports `ready`, `stale`, `missing`,
   `insufficient_data`, or `failed` with an actionable reason.
8. Rebuilding one snapshot must stale only its models and adjacent drift pairs;
   rebuilding that date must not recompute unrelated ready dates.
9. Add active-policy and per-date model readiness to the service context.
10. Return partial Drift windows containing complete pairs plus missing/stale pair
    diagnostics and coverage counts.
11. Resolve Snapshot Review cluster context through the active policy for its
    selected metric/dimension, without a browser-supplied `k`.
12. Remove arbitrary operational `k` selection and legacy loader fallback from
    FastAPI. Any temporary compatibility parameter must not select a different
    policy silently.
13. Rebuild missing or stale API model dates under the active policy and audit the
    current date range.
14. Preserve the `0.6.2` guarantee that normal registered builds create no
    processed feature/model/drift files.

## In Scope

- Storage-independent registered model engine.
- Active model policy and complete policy versioning.
- Snapshot-revision staleness and readiness.
- Targeted model and adjacent-drift rebuilds.
- Partial Drift range semantics.
- FastAPI and Snapshot Review cutover to the active registered policy.
- Live API model coverage repair and verification.

## Out of Scope

- Choosing an operationally optimal `k` through new research.
- Online learning or continuous retraining.
- Forecasting, anomaly alarms, or automated maintenance decisions.
- General browser navigation redesign; that remains sprint `0.6.4`.
- Deleting legacy clustering files, tables, or diagnostic CLI commands.
- Replacing KMeans with another algorithm.
- Reworking the `0.6.2` snapshot store or export boundary.

## Migration and Compatibility Gate

1. Add policy/revision/readiness fields or replacement registered tables beside the
   current registered representation.
2. Treat existing runs as stale unless their exact snapshot revision and full
   active policy version can be proven.
3. Recompute representative mock and API dates with the extracted engine.
4. Compare deterministic assignments, centroid summaries, PCA availability,
   metrics, warnings, and drift alignment to the current registered implementation.
5. Explain and approve numerical differences outside declared tolerances before
   FastAPI cutover.
6. Cut registered repositories and FastAPI over only after browser/API parity and
   readiness tests pass.
7. Retain old registered rows, artifacts, and legacy code read-only until `0.6.6`.

Rollback restores the previous registered repository handlers and active model
selection. It must not require rebuilding source snapshots.

The legacy dimension path is not required to match the active registered model; it
is being retired because it is not the operational browser contract.

## Acceptance Criteria

1. Building an active model reads fixed SQLite facts and no feature or snapshot CSV.
2. A normal model or drift build creates no processed artifact directory.
3. The service exposes one active `k`, complete model-policy version, and supported
   metric/dimension-to-feature mapping.
4. Every ready model proves an exact current snapshot revision and policy version.
5. Rebuilding a daily snapshot makes its previous model visibly stale.
6. Rebuilding that model restores readiness and only rebuilds affected adjacent
   drift pairs.
7. Drift with a missing first, middle, or last date returns valid pairs plus an
   explicit gap instead of failing the whole range.
8. Snapshot Review uses the active model without sending `k`.
9. Operational cluster and Drift routes cannot fall back to a legacy file loader.
10. Current API dates have an auditable ready/stale/missing/insufficient/failed
    status and repaired coverage where input data is sufficient.
11. Deterministic engine results match the current registered implementation within
    documented numeric tolerances.

## Efficiency Benchmark Plan

Keep the figures separate so one-time migration work is not confused with normal
operating cost:

1. **Cold model build:** elapsed time, peak working set, peak Python allocation, and
   SQLite growth per API model-date and feature space.
2. **Drift pair build:** elapsed time and SQLite growth per adjacent pair.
3. **Warm reuse:** time and memory to recognize an already-ready model without
   recomputation.
4. **Targeted stale rebuild:** cost for one rebuilt snapshot date and its affected
   adjacent pairs versus rebuilding the full range.
5. **Web reads:** response time and payload size for Snapshot cluster context,
   a single cluster view, a complete Drift window, and a deliberately gapped window.
6. **Disk behavior:** confirm zero routine artifact-file growth; report registered
   SQLite growth separately from legacy storage retained for `0.6.6` rollback.

## Execution Evidence

- Baseline: `137 passed, 1 skipped` in 109.85 seconds.
- Final gate: `145 passed, 1 skipped` in 142.10 seconds.
- The live API store now has 88 ready active models and 84 active drift pairs over
  22 dates, with no failed or insufficient dates.
- Representative retained-v1 versus extracted-engine model and drift results were
  exact across assignments, centroids, PCA, metrics, warnings, and alignment.
- Snapshot Review resolves its cluster through metric/dimension policy mapping and
  the browser sends no `k` parameter.
- First, middle, and last model gaps return partial windows with explicit pair
  diagnostics; transaction-boundary tests prove incomplete model or drift writes
  roll back.
- See [the separate benchmark record](../benchmarks/0.6.3-registered-model-convergence.md)
  for cold, reuse, targeted rebuild, web-read, memory, and disk figures.
