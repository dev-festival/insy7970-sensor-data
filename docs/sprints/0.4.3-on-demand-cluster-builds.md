# Sprint 0.4.3 - On-Demand Cluster Builds

## Problem Statement

Sprint `0.4.0` made clusters read-only over existing CSV/JSON artifacts. That was the right first step, but parameter-driven exploration makes missing artifacts feel awkward. If a user selects a valid `source`, date or date range, `dimension`, and `k`, the natural workflow is to build or reuse that result deliberately.

This sprint adds explicit on-demand cluster building from the durable local working layer. It should not make ordinary `GET` requests mutate storage, and it should not call the live Waites API. It should compute from existing daily snapshots and SQLite-backed snapshot facts, persist normal CSV/JSON artifacts, and then return the same response shape as the read-only endpoints.

## Architecture Decisions

1. `GET` endpoints remain read-only.
2. On-demand computation uses deliberate `POST /ensure` routes or equivalent CLI-backed commands.
3. Daily snapshots and the ingestion ledger remain the durable input layer.
4. Cluster results remain CSV/JSON artifacts after computation.
5. `k` remains an exploration parameter.
6. Drift and cluster-window builds must keep `source`, date range, `dimension`, `k`, random seed, and feature policy consistent.
7. The API should reuse existing artifacts when the exact requested result already exists and is valid.
8. A failed build should return a useful error and must not leave partial artifacts presented as complete.

## Requirements

1. Add explicit ensure endpoints for single-date clusters and cluster windows.
2. Ensure endpoints must compute only from existing local daily snapshots or SQLite daily snapshot rows.
3. Ensure endpoints must not fetch live Waites data.
4. Ensure endpoints must reuse valid existing artifacts unless `force=true` is passed.
5. Ensure endpoints must persist the same artifact contract used by CLI clustering commands.
6. Ensure endpoints must return the same payload shape as the corresponding read-only `GET` endpoint after success.
7. Add browser UI states for missing cluster/window artifacts: "Build result" and "Built/reused result".
8. Add concurrency/rerun safeguards so repeated clicks do not corrupt artifacts.
9. Add clear API errors for missing daily snapshots, invalid `k`, unsupported dimensions, and too-few feature rows.
10. Keep the CLI as a first-class build surface; API ensure behavior should delegate to the same core functions as the CLI.

## Proposed API Shape

Exact payloads can settle during implementation, but the intended routes are:

```text
POST /api/clusters/ensure
POST /api/cluster-windows/ensure
```

Example request:

```json
{
  "source": "api",
  "date": "2026-07-25",
  "dimension": "x",
  "k": 5,
  "random_seed": 42,
  "force": false
}
```

Example cluster-window request:

```json
{
  "source": "api",
  "start_date": "2026-07-24",
  "end_date": "2026-07-26",
  "dimension": "x",
  "k": 4,
  "random_seed": 42,
  "force": false
}
```

Example response metadata:

```json
{
  "status": "reused",
  "artifact_state": "complete",
  "source": "api",
  "dimension": "x",
  "k": 4,
  "payload": {}
}
```

`status` should distinguish at least:

```text
reused
built
failed
```

## Compute Source Policy

The default compute source should be:

```text
SQLite daily snapshots when available
```

CSV snapshot artifacts may remain a fallback because they are part of the current artifact contract. The sprint should make the choice explicit in metadata so users can tell whether a result was built from SQLite daily rows or snapshot CSVs.

## Browser Flow

```text
user selects source/date range/dimension/k
browser tries the read-only GET endpoint
if artifact exists, render it
if artifact is missing, show Build result
user clicks Build result
browser sends POST ensure request
API builds or reuses artifacts
browser renders returned payload
```

The UI should avoid automatic computation on page load. The action must be deliberate.

## In Scope

- `POST /api/clusters/ensure`.
- `POST /api/cluster-windows/ensure`.
- Reuse of existing core clustering/window functions.
- Browser missing-artifact build action.
- Force rebuild option if easy to expose safely.
- Tests for built, reused, invalid, and missing-input states.
- Documentation for on-demand compute behavior.

## Out of Scope

- Mutating `GET` routes.
- Fetching live Waites data from the web request path.
- Long-running background job infrastructure.
- Multi-user build queues.
- Persisting cluster rows into SQLite as the primary result store.
- Source-detail drilldown.
- Maximo integration.
- Authentication or role-based permissions.

## Safety Notes

The first implementation can run synchronously because current cluster builds are small enough. If build time becomes noticeable, a later sprint can add background jobs or task status endpoints.

Ensure routes should be careful with partial output. If an underlying build fails, the API should return a failure response and the browser should continue showing the missing/failed state rather than pretending a result exists.

## Test Out Plan

- Run `uv run pytest`.
- Test ensure cluster builds a missing artifact from prepared mock snapshots.
- Test ensure cluster reuses an existing artifact when `force=false`.
- Test ensure cluster rebuilds when `force=true`.
- Test ensure cluster-window builds adjacent drift and aligned drift artifacts.
- Test missing snapshots return a useful 404 or 422 response.
- Test invalid dimension and `k` return useful validation responses.
- Test read-only `GET` endpoints remain non-mutating.
- Manually verify the browser shows a missing-artifact build action and renders the result after success.

## Next Sprint Lead In

After on-demand cluster builds exist, the dashboard can support parameter exploration without precomputing every combination. Later `0.4.x` work can add source-detail drilldown, cluster result registry/indexing, or a background build queue if synchronous compute becomes too limiting.
