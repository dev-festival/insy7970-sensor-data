# Sprint 0.2.8 - Clustering Feature Contract

## Problem Statement

Clustering should not begin by guessing which columns are features, how missing measurements are handled, or how success will be judged. The project needs one small bridge sprint between evidence reporting and clustering implementation. This sprint defines the feature matrix contract, missingness policy, and readiness checks that `0.3.0` will consume.

## Requirements

1. Define the initial clustering feature set from daily sensor snapshot columns.
2. Build dimension-specific feature matrices for X, Y, Z, and temperature rather than blending unlike measurements into a default composite.
3. Exclude identifiers, names, dates, asset numbers, source metadata, and fields that would leak labels rather than describe behavior.
4. Define a missing-value policy for numeric features.
5. Define minimum data requirements for a cluster run: minimum sensors, minimum non-null features, and minimum usable rows.
6. Add a feature matrix builder that can write a preview artifact without running clustering.
7. Add `sensor-data cluster features --date YYYY-MM-DD --source mock` or equivalent preview command.
8. Write feature readiness artifacts under `data/processed/features/`.
9. Add feature readiness output to the evidence report when available.
10. Document which features are included and why.

## In Scope

- Feature selection contract.
- Dimension-specific X, Y, Z, and temperature feature matrices.
- Missingness and imputation rules.
- Feature matrix preview artifact.
- Feature summary artifact with null counts, usable feature counts, and excluded columns.
- Tests over deterministic mock snapshots.
- Documentation that lets a human inspect whether the clustering input makes sense.

## Initial Feature Policy

The first clustering feature set should start conservative:

- Include daily numeric behavior columns from `sensor_snapshot.csv`, such as RMS, ImpactVue, and temperature summary metrics.
- Treat X, Y, Z, and temperature as separate like-for-like clustering dimensions. The default preview should write one feature matrix per dimension.
- Include axis-specific RMS features for the matching vibration axis. Do not include Y columns in an X matrix, and do not include X columns in a Y or Z matrix.
- Include temperature summary fields in a dedicated `temperature` matrix. Do not blend temperature into the X, Y, or Z vibration matrices.
- Exclude current ImpactVue snapshot columns from the initial contract until their role is explicit. A future composite or context-augmented model can be added deliberately, but it should not be the default.
- Exclude identifiers and labels: installation point ID, equipment ID, sensor ID, names, asset numbers, source dates, source mode, and file paths.
- Exclude columns that are entirely null or below a minimum non-null threshold.
- Impute missing numeric feature values with a simple documented policy, likely per-feature median for the selected date.
- Record imputed values or imputation counts in metadata.
- Keep feature scaling in `0.3.0`; this sprint only prepares raw numeric feature matrices and readiness summaries.

## Suggested Artifacts

```text
data/processed/features/
  date=2025-07-09_source=mock/
    feature_matrix_x.csv
    feature_summary_x.csv
    feature_matrix_y.csv
    feature_summary_y.csv
    feature_matrix_z.csv
    feature_summary_z.csv
    feature_matrix_temperature.csv
    feature_summary_temperature.csv
    metadata.json
```

Each `feature_matrix_DIMENSION.csv` should contain one row per sensor/installation point plus the selected numeric feature columns for that dimension. Each `feature_summary_DIMENSION.csv` should explain each candidate feature:

```text
dimension
feature
included
reason
non_null_count
null_count
imputed_count
imputation_value
mean
min
max
```

## Readiness Gates

The preview command should fail or warn clearly when:

- The snapshot artifact is missing.
- Too few sensors are available.
- Too few numeric feature columns survive filtering.
- Too many rows require imputation.
- A feature has zero variance.

Warnings are acceptable for mock data as long as they are explicit and tested. Hard failures should prevent `0.3.0` clustering from producing misleading artifacts.

## Out of Scope

- Running KMeans or any clustering algorithm.
- PCA coordinates.
- Cluster labels, cluster summaries, or drift comparison.
- Web UI changes.
- Maximo overlays.
- Automated feature selection beyond the documented rules.

## Test Out Plan

- Run `uv run pytest`.
- Test feature selection excludes identifier and metadata fields.
- Test X, Y, and Z feature matrices only include matching-axis RMS fields.
- Test the temperature feature matrix includes temperature fields and excludes vibration fields.
- Test ImpactVue columns are excluded with an explicit reason.
- Test numeric snapshot metric fields are included when sufficiently populated.
- Test feature summary records null counts and excluded-column reasons.
- Test missing values are imputed according to the documented policy.
- Test feature matrix generation is deterministic for the mock snapshot.
- Test readiness failures or warnings for too-small inputs.

## Next Sprint Lead In

Sprint `0.3.0` uses this feature contract to run deterministic clustering. With the input matrix already documented and tested, clustering can focus on scaling, KMeans behavior, metrics, PCA coordinates, and drift artifacts.
