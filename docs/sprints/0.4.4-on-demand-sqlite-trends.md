# Sprint 0.4.4 - On-Demand SQLite Trends

## Problem Statement

The current Trend tab depends on prebuilt trend artifacts. That was useful while proving the early processed-output contract, but it creates unnecessary browser friction now that daily snapshot facts are persisted in SQLite.

Trend is not a fitted model. It is a deterministic query over daily facts:

```text
source
date range
scope
metric
dimension
aggregation/statistic
```

If the daily snapshot rows exist in `sensor_daily_snapshots`, the app should be able to return trends on request without requiring a separate trend artifact build.

## Working Decision

Move the normal web Trend path to read directly from SQLite.

Trend artifacts under `data/processed/trends/` remain useful for reports, exports, and backwards compatibility, but they should no longer be required for routine browser rendering.

`GET /api/trends` stays read-only. It should compute the response from existing SQLite daily snapshot rows and should not write trend CSV/JSON artifacts as a side effect.

## Why Trend Is Different From Clustering

Trend can be runtime because it is cheap and directly derived from persisted daily facts.

Clustering stays offline because a cluster result has model identity:

```text
feature policy
scaler policy
algorithm
random seed
k
dimension
centroid alignment
input snapshot identity
```

Trend has query parameters. Clustering has model provenance.

## Query Inputs

`GET /api/trends` should support:

```text
source
start_date
end_date
scope
asset_tree_id
equipment_id
installation_point_id
sensor_id
customer_asset_id
metric
dimension
stat
```

The first implementation can keep existing query compatibility:

```text
source
start_date
end_date
equipment_id
installation_point_id
customer_asset_id
```

Then the browser can pass richer scope fields once the API supports them cleanly.

## Supported Metrics

Use the daily snapshot columns already stored in SQLite.

Initial metric families:

```text
rms_vel
rms_accel
rms_pkpk
rms_cf
impact
temp_sensor
temp_ambient
```

Axis-specific metrics use:

```text
dimension = x | y | z
```

Non-axis metrics ignore `dimension`.

Initial statistics:

```text
mean
max
min
std
```

## Response Shape

Keep the existing `/api/trends` response shape where practical so the browser does not need a large rewrite.

Recommended response:

```json
{
  "source": "api",
  "start_date": "2026-07-24",
  "end_date": "2026-07-26",
  "input": "sqlite",
  "metric": "rms_vel",
  "dimension": "x",
  "stat": "mean",
  "sensor_row_count": 2514,
  "filtered_sensor_row_count": 9,
  "equipment_row_count": 12,
  "filtered_equipment_row_count": 1,
  "skipped_dates": [],
  "source_mismatch_dates": [],
  "filters": {},
  "sensor_rows": [],
  "equipment_rows": []
}
```

The route may include a metadata block explaining whether it served from:

```text
sqlite
artifact_fallback
```

## SQLite Query Policy

Default to:

```text
sensor_daily_snapshots
```

This table contains one row per source/date/installation point and already carries the daily min/mean/max/std fields needed by trend views.

Do not query timestamp-native Waites observation tables for routine Trend rendering. Those rows may be purged by release-mode workflows.

## Scope Policy

The Trend endpoint should support the same scope semantics as the navigator:

```text
all
asset_tree
equipment
sensor
```

Implementation options:

1. Join against Waites reference tables and equipment tree helpers server-side.
2. Accept child `equipment_id` or `installation_point_id` filters for the first pass and keep asset-tree filtering client-side.

Prefer server-side scope filtering once it stays simple and testable. Avoid duplicating large tree-filter logic in browser code if the API can own it.

## Artifact Fallback

If SQLite daily snapshots are unavailable, the endpoint may fall back to existing trend artifacts for backwards compatibility.

Recommended behavior:

```text
1. Try SQLite daily snapshot rows.
2. If no SQLite rows exist for the requested range, try existing trend artifact.
3. If neither exists, return a clear 404-style missing-data response.
```

The response should disclose the input source.

## Browser Behavior

The Trend tab should no longer say "missing artifact" when daily snapshot rows exist.

Normal flow:

```text
user selects source/date range/scope/metric/dimension/stat
browser calls GET /api/trends
API queries SQLite daily facts
browser renders returned rows
```

The Snapshot trend panel from `0.4.1b` should use the same API path once this sprint lands.

## CLI Behavior

Keep `sensor-data trend build` as an explicit artifact/export/report command.

Do not remove trend artifact support. Reframe it:

```text
trend build = materialize a report/export artifact
GET /api/trends = read/query daily facts for the app
```

## In Scope

- SQLite-backed trend query helper.
- `/api/trends` SQLite-first loader.
- Existing trend artifact fallback.
- Metric/dimension/stat parameter support where practical.
- Scope filtering aligned with the equipment tree model.
- Browser Trend tab update to rely on runtime trend reads.
- Snapshot trend panel reuse of the same response shape if it is already present.
- Tests for SQLite trends across mock date ranges, source filtering, equipment filtering, sensor filtering, missing dates, and artifact fallback.
- Documentation that trend artifacts are optional for the web path.

## Out of Scope

- Runtime cluster computation.
- Cluster model registry work from `0.4.3`.
- Timestamp-level source drilldown.
- Live Waites API requests from trend endpoints.
- Writing trend artifacts as a side effect of `GET /api/trends`.
- Maximo integration.
- User-authored alert thresholds or forecasts.

## Test Out Plan

- Run `uv run pytest`.
- Test `/api/trends` returns rows from SQLite when daily snapshots exist and no trend artifact exists.
- Test source filtering prevents mock/API range mixing.
- Test equipment and sensor filters return expected rows.
- Test missing dates are reported without crashing when at least one date exists.
- Test missing SQLite rows and missing artifacts return a clear missing-data response.
- Test `sensor-data trend build` still writes CSV/JSON artifacts.
- Run `node --check src/insy_sensor_data/api/static/app.js`.
- Smoke the browser Trend tab after deleting or omitting trend artifacts but keeping SQLite daily snapshots.

## Next Sprint Lead In

After trends become SQLite-backed, the browser will no longer depend on prebuilt trend artifacts for routine review. Later `0.4.x` work can add timestamp-level source drilldown for suspicious daily points without changing the durable daily snapshot contract.
