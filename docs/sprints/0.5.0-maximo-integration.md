# Sprint 0.5.0 - Maximo Integration

## Problem Statement

Sensor data becomes more valuable when it is aligned with maintenance history. This sprint adds a Maximo data boundary that can use DB2/ODBC in production and mock fixtures in development, joining records to Waites equipment through asset number alignment.

The primary product surface is the existing Snapshot **Events** log. It must combine
Waites action items and Maximo work orders without making an unbounded Maximo query
when the browser is in its default **All Equipment** scope.

## Working Decisions

### Activation boundary

Maximo work orders are loaded only after the reviewer selects an Asset Tree. The
selected tree supplies a bounded, distinct set of non-empty Waites
`customer_asset_id` values, which are aligned to Maximo `assetnum` values.

- **All Equipment** must not issue a Maximo query. The Events pane continues to show
  its normal Waites events and explains that Maximo history requires an Asset Tree
  selection.
- An Asset Tree selection loads work orders for the assets represented by that tree
  and the selected Snapshot date range.
- A later equipment or sensor selection filters the already-loaded Asset Tree event
  set; it must not trigger a broader Maximo lookup.
- Department-scoped activation is deferred. The current browser model has no
  department filter or authoritative department-to-asset mapping. It can be added
  later as a second bounded activation mode once that mapping is defined.

### Event contract

The Snapshot review response remains the browser's single data request. Its `events`
section merges existing Waites action-item rows with normalized Maximo work-order rows
and retains a source/status summary for each provider. A Maximo connection or query
failure is reported as partial event availability; it must not prevent the Snapshot,
Waites events, trends, or measurements from rendering.

Normalized Maximo rows use the existing table vocabulary:

```text
date           <- REPORTDATE
source         <- "maximo"
status         <- STATUS
type           <- WORKTYPE
asset_number   <- matched ASSETNUM
event_id       <- WONUM
work_order     <- WONUM
title          <- DESCRIPTION
```

Rows are deduplicated by matched asset number and work order number, then sorted by
date descending and work order number. The existing Waites event fields remain
unchanged.

## Requirements

1. Add Maximo configuration for DSN, schema, site ID, query timeout, and mock mode
   without committing credentials. A server-managed DSN is the default credential
   mechanism; the application must not commit credentials.
2. Add a query loader for parameterized SQL files using positional ODBC parameters.
3. Implement a read-only work-order history query by `assetnum`, site, and date
   range. Parameter markers must be unquoted ODBC `?` markers. The query must
   correctly return a match through either `WORKORDER.ASSETNUM` or
   `MULTIASSETLOCCI.ASSETNUM`, without duplicate or misattributed rows.
4. Add fixture-backed Maximo mock data so tests and local demos do not require DB2 access.
5. Join Maximo asset history to Waites equipment using `customer_asset_id` aligned to Maximo `assetnum`.
6. Merge normalized Maximo work orders into the Snapshot Events log under the
   selected Asset Tree activation rule.
7. Add `sensor-data maximo asset-history --assetnum VALUE --source mock` as a
   diagnostic interface over the same core query boundary.
8. Expose the diagnostic asset-history lookup through the API, while the browser
   continues to use `/api/snapshot-review/{date}` rather than making a second request.

## In Scope

- Read-only DB2/ODBC access boundary.
- Query file organization.
- Mock Maximo fixtures.
- Asset history CLI command.
- Core join logic between Waites and Maximo data.
- API endpoint for diagnostic maintenance-history lookup.
- Maximo rows composed into the Snapshot Events log for selected Asset Tree scope.
- Provider-level availability and error reporting in the Events response.

## Out of Scope

- Writing to Maximo.
- Full CMMS replication.
- User authentication.
- Report scheduling.
- Advanced work order forecasting.
- Production deployment.
- Department-scoped Maximo loading until a department filter and its asset mapping are
  explicitly defined.
- Any Maximo query for the default All Equipment browser scope.

## Test Out Plan

- Run `uv run pytest` with mock Maximo fixtures.
- Test SQL query loading and missing-query behavior.
- Test ODBC parameter ordering without requiring a live DB2 connection.
- Test asset alignment joins preserve unmatched Waites equipment and unmatched Maximo records where appropriate.
- Test CLI asset-history command returns stable fixture-backed output.
- Test API maintenance endpoint returns useful empty results for unknown assets.
- Test that All Equipment causes no Maximo provider call.
- Test that an Asset Tree loads only its distinct, non-empty customer asset IDs and
  that equipment/sensor selection filters those returned events.
- Test that a Maximo provider failure leaves Waites events and the remainder of the
  Snapshot review response available.
