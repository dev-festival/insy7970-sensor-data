# Sprint 0.3.1 - Operating Window and Cluster Interpretation

## Problem Statement

Sprint `0.2.9` changed the pipeline posture: live raw endpoint payloads and timestamp-native SQLite observations are no longer the default working set after daily snapshot persistence. Sprint `0.3.0` then proved deterministic dimension-specific clustering over those snapshots. The next useful step is not deeper memory machinery; it is a clear operating-window workflow and a more honest interpretation layer for cluster quality and drift.

This sprint should let an operator process a small live or mock date window one day at a time, run clusters consistently, compare adjacent days, and understand what the metrics mean. Drift should stop relying only on same-number KMeans labels and should add centroid alignment before deciding whether a sensor truly changed behavioral groups.

## Requirements

1. Add a date-window workflow that processes each date independently through the existing daily path: fetch, validate, load, snapshot CSV and SQLite storage, raw/native retention, feature build, and optional clustering.
2. Add a cluster-window helper that runs per-date clustering for a source, date range, dimension, and `k`, then compares adjacent dates.
3. Keep range processing snapshot-first: clustering and interpretation must consume daily snapshots, feature matrices, cluster artifacts, and drift artifacts, not raw endpoint payloads or timestamp-native observation rows.
4. Add centroid-aligned drift output that maps clusters from one day to the nearest compatible cluster on the next day before marking sensors as changed.
5. Save interpretation artifacts that summarize rows, feature counts, inertia, silhouette, Calinski-Harabasz, cluster counts, centroid movement, aligned changed count, and warnings by date pair.
6. Add clear caveats for small sample sizes. Mock clustering with 9 rows and `k=4` is a contract test, not a quality signal.
7. Add human-readable CLI summaries that explain whether a cluster run looks stable, noisy, too small, or label-ambiguous.
8. Preserve resume-friendly behavior: existing valid snapshots, feature matrices, cluster outputs, and drift outputs should be reused unless `--force` is passed.
9. Add tests that prove range steps run one date at a time, centroid alignment changes drift interpretation when labels move, and release-mode snapshots remain sufficient for clustering.

## In Scope

- `workflow api-range` and `workflow mock-range` style orchestration.
- `cluster window` or equivalent range helper over existing feature and cluster commands.
- Centroid mapping between adjacent cluster runs.
- Aligned cluster drift artifacts beside the existing raw label drift artifacts.
- Cluster quality summaries for operating windows.
- Human-readable interpretation text and JSON output.
- Fixture-backed tests over mock data and synthetic label-permutation cases.
- Documentation for reading first-pass clustering metrics.

## Interpretation Baseline

Recent runs provide the starting posture:

- Mock `2025-07-09`, 9 rows, `k=4`: useful for contract testing, too small to judge clustering quality.
- Live `2026-07-24`, 838 rows, 16 features, silhouette around `0.45`: a reasonable first signal.
- Live `2026-07-25`, 838 rows, 16 features, silhouette around `0.46`: similar shape day to day.
- Inertia and Calinski-Harabasz were close across `2026-07-24` and `2026-07-25`, suggesting the broad cluster structure was not wildly shifting.
- Raw label drift showed 81 of 838 matched sensors changing clusters, about `9.7%`.

That drift result is plausible, but it is not yet a final reliability metric. KMeans labels are deterministic in this project, but label numbers are still not semantic categories. Centroid alignment is required before the project treats a sensor as having truly moved between behavioral groups.

## Suggested Commands

Exact command names can settle during implementation, but the sprint should produce something close to:

```powershell
uv run sensor-data workflow api-range --start-date 2026-07-24 --end-date 2026-07-26 --facility 679 --raw-retention release --dimension x --k 4
uv run sensor-data workflow mock-range --start-date 2025-07-09 --end-date 2025-07-11 --dimension x --k 4
uv run sensor-data cluster window --source api --start-date 2026-07-24 --end-date 2026-07-26 --dimension x --k 4
uv run sensor-data cluster align-drift --source api --from-date 2026-07-24 --to-date 2026-07-25 --dimension x --k 4
```

Useful options:

```powershell
--dimensions x,y,z,temperature
--skip-fetch
--skip-cluster
--resume
--force
--max-days N
--json
```

`--resume` should be the default posture when valid artifacts already exist. `--force` should deliberately rebuild artifacts.

## Output Contract

Per-date cluster artifacts from sprint `0.3.0` should remain stable:

```text
data/processed/clusters/date=YYYY-MM-DD_source=SOURCE_dimension=DIMENSION_k=K/
```

Window interpretation should write a compact range artifact:

```text
data/processed/cluster_windows/start=YYYY-MM-DD_end=YYYY-MM-DD_source=SOURCE_dimension=DIMENSION_k=K/
    window_summary.csv
    quality_summary.csv
    aligned_drift_summary.csv
    centroid_alignment.csv
    metrics.json
```

`centroid_alignment.csv` should include at least:

```text
from_date
to_date
from_cluster
to_cluster
centroid_distance
from_sensor_count
to_sensor_count
mapping_confidence
```

`aligned_drift_summary.csv` should include at least:

```text
from_date
to_date
matched_sensor_count
raw_label_changed_count
aligned_changed_count
raw_label_changed_ratio
aligned_changed_ratio
```

## Test Out Plan

- Run `uv run pytest`.
- Test mock range orchestration processes each date independently and reports per-date status.
- Test release-mode workflow leaves enough snapshot data for feature building and clustering.
- Test cluster window outputs quality and aligned drift summaries.
- Test centroid alignment handles a synthetic label permutation where raw labels change but nearest-centroid mapping is stable.
- Test small mock windows produce an explicit "contract test only" warning.
- Test `--resume` reuses valid artifacts and `--force` rebuilds them.

## Next Sprint Lead In

After this sprint, the project should have enough cluster-window evidence to decide whether the next implementation step is dashboard/API surfacing, cluster tuning, or deferred artifact packing. Packing should wait until processed artifacts are actually large enough or old enough to justify loader complexity.
