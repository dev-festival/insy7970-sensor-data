# Sprint 0.4.3 - Offline Cluster Model Registry

## Problem Statement

Cluster results are not just another chart query. A clustering result is identified by the source data, snapshot date or operating window, feature space, `k`, feature policy, scaler policy, algorithm, random seed, and drift-alignment method. Treating that as a casual browser-time calculation makes the app feel flexible, but it also makes model identity, reproducibility, and drift interpretation harder to trust.

The project already treats daily snapshots as durable outputs of the operating pipeline. Cluster models should follow the same pattern. The pipeline should build a configured grid of cluster models in the background or CLI workflow, persist their model identity and results to SQLite, and let the web app select from those completed model runs.

## Working Decision

Move clustering from "on-demand web build" to "offline model grid + SQLite registry."

The browser should not build clusters. It should choose a prebuilt model identity:

```text
source
date or date range
feature_space
k
feature policy
random seed
```

Then it should read assignments, PCA coordinates, centroids, metrics, and drift characteristics from SQLite.

CSV/JSON artifacts remain valuable as inspectable evidence and exports, but SQLite becomes the primary read layer for the app.

## Pipeline Shape

The intended operating flow is:

```text
api-day / api-range
  -> fetch Waites evidence
  -> validate raw source shape
  -> load SQLite observations
  -> build daily snapshot CSV and SQLite rows
  -> build feature matrices
  -> build configured cluster model grid
       feature spaces: x_accel, y_vel, z_vel, temperature
       k: 5
  -> compute adjacent-date drift and centroid alignment
  -> persist cluster and drift results to SQLite
  -> optionally write CSV/JSON artifacts for inspection/export
  -> apply raw/native retention policy
```

The exact default grid can remain configurable, but the first useful default is intentionally small and operationally named:

```text
feature_spaces = [x_accel, y_vel, z_vel, temperature]
ks = [5]
random_seed = 42
feature_policy_version = current feature contract version
```

Do not bundle all metrics for an axis into one model. Axis bundles are too easy to misread in the UI and in drift interpretation. A feature space should name the metric family and axis when the metric is axis-specific.

Initial feature-space contract:

```text
x_accel      = X-axis RMS acceleration daily stats
y_vel        = Y-axis RMS velocity daily stats
z_vel        = Z-axis RMS velocity daily stats
temperature  = sensor temperature daily stats
```

The larger `k=5` default is deliberate. It gives the model a clear middle cluster while still allowing low/high behavioral groups on either side. Additional `k` values can be built explicitly later, but they should not be part of the default grid until the UI proves they are useful.

## Model Identity

Every cluster model run needs a stable identity. At minimum, persist:

```text
model_run_id
source
source_date
feature_space
k
algorithm
random_seed
feature_policy_version
feature_columns_json
scaler_policy
input_snapshot_hash
input_snapshot_row_count
feature_row_count
feature_count
status
created_at
completed_at
artifact_dir
metrics_json
warnings_json
```

The project should not rely on `date + feature_space + k` alone once these models are used operationally. If the feature contract changes, the old and new models must not be confused.

## Proposed SQLite Tables

Exact column names can settle during implementation, but the registry should include this logical shape.

### `cluster_model_runs`

One row per fitted model identity.

```text
model_run_id TEXT PRIMARY KEY
source TEXT NOT NULL
source_date TEXT NOT NULL
feature_space TEXT NOT NULL
k INTEGER NOT NULL
algorithm TEXT NOT NULL
random_seed INTEGER NOT NULL
feature_policy_version TEXT NOT NULL
feature_columns_json TEXT NOT NULL
scaler_policy TEXT NOT NULL
input_snapshot_hash TEXT
input_snapshot_row_count INTEGER NOT NULL
feature_row_count INTEGER NOT NULL
feature_count INTEGER NOT NULL
status TEXT NOT NULL
created_at TEXT NOT NULL
completed_at TEXT
artifact_dir TEXT
metrics_json TEXT
warnings_json TEXT
UNIQUE(source, source_date, feature_space, k, algorithm, random_seed, feature_policy_version)
```

### `cluster_model_assignments`

One row per sensor/installation point assigned by a model.

```text
model_run_id TEXT NOT NULL
installation_point_id TEXT NOT NULL
sensor_id TEXT
equipment_id TEXT
customer_asset_id TEXT
cluster INTEGER NOT NULL
distance_to_centroid REAL
pca_x REAL
pca_y REAL
features_json TEXT
PRIMARY KEY(model_run_id, installation_point_id)
```

### `cluster_model_centroids`

One row per cluster centroid.

```text
model_run_id TEXT NOT NULL
cluster INTEGER NOT NULL
sensor_count INTEGER NOT NULL
centroid_json TEXT NOT NULL
pca_x REAL
pca_y REAL
summary_json TEXT
PRIMARY KEY(model_run_id, cluster)
```

### `cluster_drift_runs`

One row per adjacent-date or window drift interpretation.

```text
drift_run_id TEXT PRIMARY KEY
from_model_run_id TEXT NOT NULL
to_model_run_id TEXT NOT NULL
source TEXT NOT NULL
from_date TEXT NOT NULL
to_date TEXT NOT NULL
feature_space TEXT NOT NULL
k INTEGER NOT NULL
alignment_policy TEXT NOT NULL
matched_sensor_count INTEGER NOT NULL
raw_changed_sensor_count INTEGER NOT NULL
aligned_changed_sensor_count INTEGER NOT NULL
status TEXT NOT NULL
metrics_json TEXT
warnings_json TEXT
created_at TEXT NOT NULL
```

### `cluster_drift_assignments`

One row per matched or unmatched sensor in a drift comparison.

```text
drift_run_id TEXT NOT NULL
installation_point_id TEXT NOT NULL
from_cluster INTEGER
to_cluster INTEGER
aligned_to_cluster INTEGER
status TEXT NOT NULL
raw_changed INTEGER NOT NULL
aligned_changed INTEGER NOT NULL
distance_delta REAL
PRIMARY KEY(drift_run_id, installation_point_id)
```

### `cluster_centroid_alignment`

One row per centroid mapping between two model runs.

```text
drift_run_id TEXT NOT NULL
from_cluster INTEGER NOT NULL
to_cluster INTEGER
distance REAL
mapping_confidence TEXT
PRIMARY KEY(drift_run_id, from_cluster)
```

## CLI / Workflow Requirements

Add a first-class command or workflow option for building the grid.

Implemented command shape:

```powershell
uv run sensor-data cluster registry build-grid --source api --start-date 2026-07-24 --end-date 2026-07-26 --feature-spaces x_accel,y_vel,z_vel,temperature --ks 5
```

The final command shape can follow existing Typer patterns, but it should:

1. Build from existing daily snapshots or SQLite daily snapshot rows.
2. Reuse completed model runs unless `--force` is passed.
3. Build each date/feature-space/`k` independently.
4. Build adjacent-date drift only when both model runs are complete.
5. Persist successful model and drift rows to SQLite.
6. Mark failed/incomplete runs clearly and avoid presenting them as usable.
7. Still write CSV/JSON artifacts if the existing cluster artifact contract is cheap to preserve.

`workflow api-range` and `workflow mock-range` call this grid builder when `--cluster-models` is provided:

```powershell
uv run sensor-data workflow api-range --start-date 2026-07-24 --end-date 2026-07-26 --facility 679 --raw-retention release --cluster-models
```

The workflow reports how many models were built, reused, skipped, or failed.

## API Requirements

The app should read from SQLite first.

Read endpoints should support:

```text
GET /api/clusters?source=api&date=YYYY-MM-DD&feature_space=x_accel&k=5
GET /api/drift?source=api&from_date=YYYY-MM-DD&to_date=YYYY-MM-DD&feature_space=x_accel&k=5
GET /api/cluster-windows?source=api&start_date=YYYY-MM-DD&end_date=YYYY-MM-DD&feature_space=x_accel&k=5
```

Those routes may keep their current response shape, but their loader should prefer registered SQLite model runs. CSV/JSON artifact fallback can remain during the transition.

Add a model discovery endpoint if it helps the browser avoid dead controls:

```text
GET /api/cluster-models?source=api&start_date=YYYY-MM-DD&end_date=YYYY-MM-DD
```

Suggested response:

```json
{
  "source": "api",
  "start_date": "2026-07-24",
  "end_date": "2026-07-26",
  "feature_spaces": ["x_accel", "y_vel", "z_vel", "temperature"],
  "ks": [5],
  "models": [
    {
      "model_run_id": "api:2026-07-24:x_accel:k5:v1",
      "date": "2026-07-24",
      "feature_space": "x_accel",
      "k": 5,
      "status": "complete",
      "feature_row_count": 838,
      "silhouette_score": 0.21
    }
  ]
}
```

## Browser Behavior

The browser should present `feature_space` and `k` as selectors over available registered models.

Recommended labels:

```text
x_accel      -> X Acceleration
y_vel        -> Y Velocity
z_vel        -> Z Velocity
temperature  -> Temperature
```

If a selected combination does not exist, show a small empty state:

```text
No registered cluster model for this date, feature space, and k.
```

Do not show a browser "Build" button in this sprint. Rebuild controls belong to operator workflows or a later admin surface.

Scope selection continues to filter display rows only:

```text
cluster compute scope: completed registered model
cluster display scope: all / asset tree / equipment / sensor
drift compute scope: completed registered drift run
drift display scope: all / asset tree / equipment / sensor
```

## In Scope

- SQLite schema for cluster model runs, assignments, centroids, drift runs, drift assignments, and centroid alignment.
- Registry persistence from existing cluster and cluster-window builders.
- Configurable offline model grid, with `x_accel`, `y_vel`, `z_vel`, `temperature`, and `k=5` as the first practical default.
- CLI/workflow build path for the configured model grid.
- SQLite-first cluster, drift, and cluster-window API loaders.
- Optional CSV/JSON artifact writes for inspection/export compatibility.
- Model discovery endpoint if useful for the UI.
- Tests for model identity, reuse, force rebuild, incomplete runs, and SQLite/API response parity.
- Documentation explaining cluster model identity and the difference between model build and model selection.

## Out of Scope

- Browser-time cluster computation.
- `POST /api/clusters/ensure` or similar web build endpoints.
- Fetching live Waites data from cluster model requests.
- Full background job scheduler or multi-user queue.
- Persisting timestamp-native raw readings for cluster inspection.
- Maximo integration.
- Authentication, authorization, and admin rebuild permissions.

## Safety Notes

Use transactions when persisting each model run and drift run. A failed model build should not leave assignment rows attached to a `complete` run.

Prefer explicit statuses:

```text
pending
running
complete
failed
skipped
```

The browser should only render `complete` model runs by default.

## Test Out Plan

- Run `uv run pytest`.
- Test registry tables initialize cleanly.
- Test a mock cluster grid persists the default feature spaces with `k=5`.
- Test assignments, centroids, metrics, PCA coordinates, and warnings are available through SQLite.
- Test adjacent-date drift rows and centroid alignment persist when both model runs exist.
- Test repeated grid builds reuse completed runs unless `force=true`.
- Test failed runs are marked failed and are not returned as complete API results.
- Test existing CSV/JSON cluster API responses match SQLite-backed responses for the same model.
- Smoke the browser with prebuilt `x_accel`, `y_vel`, `z_vel`, and `temperature` mock models at `k=5`.
