# Sprint 0.4.0 - API and Static Web Hardening

## Problem Statement

The project already has a FastAPI service, static app shell, SQLite-backed daily snapshots, trend artifacts, clustering artifacts, snapshot-release ingestion, and operating-window cluster interpretation by this point. This sprint hardens the browser-accessible surface for daily review without moving business logic into route handlers or browser JavaScript.

The front end should make the existing operating layer visible first. It should not require every possible cluster setting to be predefined or precomputed, but it also should not silently compute and mutate project state from ordinary page loads. Cluster results are parameterized analysis artifacts: `source`, date or window, `dimension`, `k`, random seed, feature schema, and input snapshot identity define a result. Once computed, the result is reusable.

## Architecture Decisions

1. Daily snapshots and the ingestion ledger remain the durable source of truth for local operating facts.
2. Cluster rows remain CSV artifacts for now, with JSON metrics/provenance beside them.
3. SQLite is not the primary cluster result store in this sprint.
4. `k` is an exploration parameter, not an architectural constant.
5. Drift and cluster-window views must hold `source`, `dimension`, `k`, feature policy, and date range constant.
6. `GET` API routes in this sprint are read-only over existing artifacts.
7. Missing cluster artifacts should be treated as a normal UI/API state, not as an error that triggers hidden computation.
8. Future on-demand compute should use deliberate `ensure` style commands or endpoints, not mutating `GET` requests.

## Requirements

1. Expand FastAPI endpoints for artifact discovery, equipment lookup, cluster results, drift results, cluster-window results, and richer snapshot detail responses.
2. Preserve existing health, raw-run, snapshot, and trend endpoints while tightening response schemas and error handling.
3. Add core loader functions for cluster, drift, cluster-window, equipment, and artifact-discovery payloads.
4. Keep route handlers thin by delegating loading, filtering, and response shaping to core modules.
5. Serve the static HTML/CSS/JS app from the API process for local development and mock/API artifact review.
6. Render snapshot, trend, cluster, and drift views using Plotly.js against API responses.
7. Let the browser select available `source`, date or date range, `dimension`, and `k` combinations.
8. Show a clear missing-artifact state when a selected cluster or drift result has not been built yet.
9. Keep `sensor-data serve --source mock` as the single local service startup command.
10. Document local API and web startup in the README.

## Proposed API Shape

Exact names can settle during implementation, but the sprint should produce routes close to:

```text
GET /health
GET /api/dates
GET /api/artifacts
GET /api/waites/raw-runs
GET /api/equipment?source=api
GET /api/snapshots/{date}?source=api&equipment_id=VALUE&installation_point_id=VALUE
GET /api/trends?source=api&start_date=YYYY-MM-DD&end_date=YYYY-MM-DD
GET /api/clusters?source=api&date=YYYY-MM-DD&dimension=x&k=4
GET /api/drift?source=api&from_date=YYYY-MM-DD&to_date=YYYY-MM-DD&dimension=x&k=4
GET /api/cluster-windows?source=api&start_date=YYYY-MM-DD&end_date=YYYY-MM-DD&dimension=x&k=4
```

The API should return enough metadata for the browser to explain what it is showing:

```text
source
date or date range
dimension
k
row counts
feature counts
input artifacts
metrics
warnings
interpretation
rows
```

## Static Web Viewing Modes

The first browser surface should be barebones but real. It should prioritize inspection over dashboard polish.

1. Snapshot mode: one date, all sensors, filterable by equipment, asset, or installation point.
2. Trend mode: one equipment or sensor across a selected date range.
3. Cluster mode: all sensors for one `source`, date, `dimension`, and `k`, with PCA scatter and cluster summary.
4. Drift mode: adjacent-date or window view for one `source`, date range, `dimension`, and `k`, with aligned drift counts and warning text.

## Cluster Artifact Policy

Cluster artifacts remain plain and inspectable:

```text
data/processed/clusters/date=YYYY-MM-DD_source=SOURCE_dimension=DIMENSION_k=K/
  sensor_clusters.csv
  cluster_summary.csv
  pca_coordinates.csv
  metrics.json
```

Drift and cluster-window artifacts remain plain and inspectable:

```text
data/processed/drift/from=YYYY-MM-DD_to=YYYY-MM-DD_source=SOURCE_dimension=DIMENSION_k=K/
data/processed/cluster_windows/start=YYYY-MM-DD_end=YYYY-MM-DD_source=SOURCE_dimension=DIMENSION_k=K/
```

CSV is the canonical tabular cluster result for this sprint. JSON is the canonical provenance and metrics payload. A SQLite cluster registry can be added later if artifact discovery becomes slow or awkward, but it should not replace the CSV/JSON contract yet.

## In Scope

- FastAPI response schema hardening.
- Read-only API endpoints for processed snapshots, trends, clusters, drift, cluster windows, and equipment/reference lookup.
- Core artifact discovery helpers.
- Browser controls for source, date range, dimension, `k`, equipment, and sensor.
- Plotly-based trend and cluster views.
- A basic drift/window view with aligned-drift interpretation.
- Basic browser-friendly error and missing-data states.
- API tests with FastAPI's test client.
- Static smoke tests for expected app elements and asset paths.
- README updates for local API and web review.

## Out of Scope

- Authentication and user profiles.
- Deployment hardening.
- Real Waites API calls from the web request path.
- API-triggered cluster computation.
- Mutating `GET` routes.
- Precomputing cluster model grids.
- Persisting cluster result rows into SQLite as the primary store.
- Parquet or processed-artifact packing.
- Maximo ODBC connection.
- Background refresh jobs.
- Complex dashboard customization.

## Future Follow-On

After the read-only web/API surface is proven, later `0.4.x` sprints can improve parameterized reads without moving model fitting into the browser request path.

```text
0.4.3: offline cluster model registry persisted to SQLite
0.4.4: SQLite-backed trend queries over daily snapshots
```

Cluster CSV/JSON artifacts can remain inspectable evidence, but the app should eventually read registered cluster model identities from SQLite. Trend artifacts can remain report/export outputs, but routine trend API calls can be computed from SQLite daily snapshots.

## Test Out Plan

- Test API responses are JSON serializable and stable for fixture data.
- Test artifact discovery reports available snapshots, trends, clusters, drift pairs, and cluster windows.
- Test snapshot and trend endpoints preserve existing behavior.
- Test cluster endpoint reads `sensor_clusters.csv`, `cluster_summary.csv`, `pca_coordinates.csv`, and `metrics.json`.
- Test drift endpoint reads raw and aligned drift artifacts.
- Test cluster-window endpoint reads quality and aligned-drift summaries.
- Test missing processed files return useful non-500 responses.
- Test invalid dates, dimensions, and `k` values return useful validation responses.
- Test `sensor-data serve --help` starts from the CLI layer.
- Add a small static smoke test that checks expected HTML element IDs or asset paths exist.
