# Sprint 0.4.1a - Equipment Tree and Selection Behavior

## Problem Statement

Sprint `0.4.1` established the first useful global context and equipment navigation model, but the equipment selector is still too flat. The normal review path is hierarchical: start from an asset tree, expand into equipment, then inspect one or more sensors or installation points.

This sprint narrows the next revision to that hierarchy and the selection behavior behind it. It should not solve calendar inputs, chart rendering, runtime clustering, or filter-builder work. The goal is to make the selected operational scope clear, stable, URL-backed, and reusable by every tab.

## Working Decision

Use `asset_tree_id` from the Waites equipment reference layer as the top-level navigation join key, and use the Waites asset-tree endpoint as the naming/topology source when it is available.

The preferred source is SQLite reference data:

```text
waites_asset_tree_reference.asset_tree_id
waites_asset_tree_reference.name
waites_asset_tree_reference.parent_asset_tree_id
waites_asset_tree_reference.facility_id
waites_asset_tree_reference.asset_tree_path
waites_equipment_reference.asset_tree_id
waites_equipment_reference.equipment_id
waites_equipment_reference.name
waites_equipment_reference.customer_asset_id
waites_installation_point_reference.installation_point_id
waites_installation_point_reference.sensor_id
waites_installation_point_reference.name
waites_installation_point_reference.customer_asset_id
```

The Waites reference pull should include:

```text
GET /asset-tree?facility[]=679
```

The exact response shape should be normalized after inspecting real or fixture payloads. The durable project contract should only require the fields the navigator needs: a stable asset tree ID, a display name, an optional parent ID, an optional facility ID, and an optional path or breadcrumb if the endpoint provides one.

Daily snapshot rows can still determine which equipment and sensors are active inside the selected source/date context, but they should not be the only source of tree identity. If a fixture or older local database lacks asset-tree reference rows, the helper may fall back to the current `asset_tree_id` from equipment reference or snapshot-derived equipment rows.

## Tree Shape

The navigator should render the selection surface as:

```text
[+] Asset Tree Name
  [+] Equipment Name
    Sensor / Installation Point 1
    Sensor / Installation Point 2
    Sensor / Installation Point 3
```

Use the most useful available label at each level:

```text
asset tree: asset_tree_name, with asset_tree_id as supporting text
equipment:  equipment_name, with equipment_id and customer_asset_id as supporting text
sensor:     installation_point_name, with installation_point_id and sensor_id as supporting text
```

If a label is missing, fall back to the stable identifier. For example, an unnamed asset tree should still show `Asset Tree 12440`, equipment without a name should still show `Equipment 33446`, and sensors without `sensor_id` should still be selectable by `installation_point_id`.

## Canonical Scope

The browser should maintain one canonical scope object:

```json
{
  "scopeType": "all",
  "assetTreeId": null,
  "equipmentId": null,
  "installationPointId": null,
  "sensorId": null
}
```

Valid `scopeType` values:

```text
all
asset_tree
equipment
sensor
```

Only one level should be selected at a time. Selecting a child replaces the parent selection. Selecting "All Equipment" clears every scoped identifier.

## Scope Semantics

`all` means no equipment or sensor filter is applied.

`asset_tree` means all equipment and sensors beneath that `asset_tree_id`.

`equipment` means all installation points beneath that `equipment_id`.

`sensor` means one installation point or sensor. Use `installation_point_id` as the primary filter key because snapshot, trend, cluster, and drift artifacts already carry it consistently. Preserve `sensor_id` as display/detail metadata.

The selected scope should be visible in the navigator and reflected in tab data loading. The app should not allow a hidden stale equipment or sensor filter to remain active after the visible selection changes.

## Tab Behavior

Snapshot and Trend should load data filtered by the selected scope.

For `asset_tree`, the browser may pass a new `asset_tree_id` query parameter if the API supports it, or derive the child `equipment_id`/`installation_point_id` set from the tree response and filter client-side as an interim step. Prefer server-side filtering if it stays simple.

Cluster and Drift need a more careful rule because clustering is conceptually "all sensors" for the selected source/date/dimension/`k`.

For this sprint:

```text
cluster compute scope: unchanged, read-only, all sensors
cluster display scope: selected tree/equipment/sensor may filter tables and selected rows
drift compute scope: unchanged, read-only, all sensors
drift display scope: selected tree/equipment/sensor may filter tables and selected rows
```

Do not add runtime clustering in `0.4.1a`. This sprint should make the selected operational scope explicit enough that `0.4.3` can later use it deliberately for runtime cluster exploration, centroid drift, and point drift.

## Search Behavior

Search should filter the tree while preserving hierarchy.

A result should remain visible if any of these fields match:

```text
asset_tree_id
asset_tree_name
asset_tree_path
equipment_id
equipment_name
equipment customer_asset_id
installation_point_id
installation_point_name
sensor_id
installation point customer_asset_id
```

When a child matches, show its parent equipment and asset tree. When equipment matches, show its asset tree and its matching or relevant sensors. Search should not mutate the selected scope unless the user clicks a result.

## Expand and Collapse Behavior

The tree should support expand/collapse at asset tree and equipment levels.

Required behavior:

1. Selecting an asset tree expands that asset tree.
2. Selecting equipment expands its parent asset tree and that equipment.
3. Selecting a sensor expands its parent asset tree and equipment.
4. Changing source or date range preserves the selected scope only if that node still exists in the new tree.
5. If the selected node no longer exists, fall back to `all` and show a small non-blocking message.
6. Search may auto-expand matching branches while the search is active.
7. Clearing search should restore the user's explicit expanded branches where practical.

Expanded branch state may stay browser-local. Selected scope must remain URL-backed.

## URL State

Replace the current flat equipment/sensor query state with explicit scope fields.

Preferred query keys:

```text
scope=all
scope=asset_tree&asset_tree_id=12440
scope=equipment&asset_tree_id=12440&equipment_id=33446
scope=sensor&asset_tree_id=12440&equipment_id=33446&installation_point_id=116795
```

Keep backwards compatibility for existing local links where practical:

```text
equipment_id=33446
installation_point_id=116795
```

Those old keys may be interpreted into the new scope object during initial state parsing.

## Visual Requirements

The navigator should feel like a compact operations tree, not a set of cards.

Required UI traits:

1. Clear expand/collapse controls.
2. A visible selected row at every selectable level.
3. Dense but readable row spacing.
4. Supporting IDs shown in smaller secondary text.
5. Counts for asset tree and equipment rows where useful.
6. Keyboard-safe buttons for selecting and expanding rows.
7. No nested card styling inside the navigator.

## In Scope

- Equipment tree response/helper.
- Waites `GET /asset-tree` fixture, validation, and reference persistence needed for named asset-tree navigation.
- Asset-tree grouping from Waites equipment reference data.
- Asset-tree labels and optional breadcrumbs from Waites asset-tree reference data.
- Joining or attaching installation point/sensor rows beneath equipment.
- Active-date metadata inside the selected source/date context.
- Tree rendering in the static web app.
- Search within the tree while preserving hierarchy.
- Selectable `all`, `asset_tree`, `equipment`, and `sensor` scope.
- URL-backed selected scope.
- Snapshot and trend requests honoring selected scope.
- Cluster and drift display honoring selected scope without changing compute behavior.
- Tests for tree construction, endpoint response shape, static DOM anchors, and core selection transitions where practical.

## Out of Scope

- Calendar-style date selection.
- Removing or redesigning the snapshot-local date control.
- Moving `k` to a top-level control.
- Runtime clustering or drift calculation.
- Home-grown SVG chart rendering.
- Plotly replacement.
- General filter-builder engine.
- Maximo integration.
- Authentication, saved profiles, or user preferences.

## Test Out Plan

- Run `uv run pytest`.
- Add or update mock Waites asset-tree fixture data with at least one named asset tree matching existing equipment `asset_tree_id` values.
- Add tests proving asset-tree reference data is validated and persisted without requiring chart or cluster rebuilds.
- Add API/core tests proving equipment rows group under `asset_tree_id`.
- Add API/core tests proving asset-tree names appear when reference data exists and stable ID fallbacks appear when it does not.
- Add tests proving sensors appear under their equipment and preserve `installation_point_id` as the primary selectable identifier.
- Add tests for source/date context filtering and fallback behavior when reference rows are missing.
- Add static app tests for tree containers, search input, all-equipment selector, and selectable tree row hooks.
- Smoke-check `node --check src/insy_sensor_data/api/static/app.js`.
- Manually start `uv run sensor-data serve --source mock --port 8011` and verify asset tree, equipment, and sensor selection update Snapshot and Trend scopes.

## Acceptance Criteria

1. A user can browse equipment as named asset tree -> equipment -> sensor.
2. A user can select any supported scope level and see the active scope clearly.
3. Snapshot and Trend views update from the selected scope.
4. Cluster and Drift do not recompute, but their displayed rows or highlighted context reflect the selected scope where the existing artifacts permit it.
5. Source/date changes do not leave stale hidden scope filters active.
6. Search remains fast and preserves the visible hierarchy of matching results.
7. Existing local URLs with `equipment_id` or `installation_point_id` continue to land on a sensible scope when possible.
