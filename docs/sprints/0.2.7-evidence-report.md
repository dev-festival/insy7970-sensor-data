# Sprint 0.2.7 - Evidence Report

## Problem Statement

The project needs an inspectable evidence layer before clustering begins. CSV files and JSON summaries prove that commands ran, but they do not help a human decide whether the data looks right, whether the mock trend behaviors are visible, or whether future cluster outputs are credible. This sprint starts a lightweight report that collects data samples, record counts, simple charts, and expected-versus-observed checks into one artifact.

## Requirements

1. Add a `sensor-data report` command group.
2. Add `sensor-data report mock-trend --start-date YYYY-MM-DD --end-date YYYY-MM-DD` to create a report for the controlled mock trend range.
3. Generate a durable report directory under `reports/`, for example `reports/mock-trend/start=2025-07-09_end=2025-07-11/`.
4. Include source evidence counts: raw endpoint record counts, SQLite load counts, snapshot row counts, and trend row counts.
5. Include small sample tables for equipment, installation points, native observations, daily snapshots, and trend rows.
6. Include charts for known mock behaviors: rising vibration, stable vibration, normalizing high vibration/temperature, temperature spike, and missing readings.
7. Include expected-versus-observed checks for the controlled mock behaviors.
8. Keep report generation deterministic and fixture-backed in tests.
9. Prefer Quarto if it is locally available, but keep a no-Quarto fallback that writes Markdown plus CSV/PNG or HTML assets where practical.

## In Scope

- Report source directory and generated report output directory.
- Markdown or Quarto report template.
- Small chart generation using a dependency already present or a deliberately chosen lightweight dependency.
- Data sample exports under the report directory.
- Expected-versus-observed checks over the current mock trend fixture contract.
- Tests that validate report files exist and contain the expected sections/checks.
- Documentation for how to generate and read the report.

## Report Shape

Suggested output:

```text
reports/
  mock-trend/
    start=2025-07-09_end=2025-07-11/
      report.qmd
      report.md
      report.html
      checks.json
      samples/
        raw_counts.csv
        sqlite_loads.csv
        sensor_snapshot_sample.csv
        sensor_trends_sample.csv
      charts/
        rising-vibration.svg
        stable-vibration.svg
        normalizing-impact.svg
        temperature-spike.svg
        missing-readings.svg
```

`report.html` is desirable when Quarto is available. `report.md`, `checks.json`, sample CSVs, and chart assets should be enough for tests and for environments where Quarto is not installed.

## Expected Checks

The initial checks should focus on the current mock contract:

| Check | Expected Behavior |
|---|---|
| `201300_rising_vibration` | `rms_vel_mean_x` increases from `2025-07-09` to `2025-07-11` |
| `201301_stable_vibration` | selected vibration metric remains nearly unchanged across the range |
| `201303_normalizing_impact` | `impact_mean` decreases across the range |
| `201307_temperature_spike` | sensor temperature peaks on `2025-07-10` |
| `201305_missing_readings` | selected reading metrics are blank or absent on `2025-07-10` |

The checks should write machine-readable results to `checks.json` and human-readable summaries into the report.

## Quarto Boundary

Quarto is useful for the eventual project narrative, but it should not become a hard dependency for the offline test suite. The implementation should:

- Detect whether `quarto` is available.
- Render HTML when available.
- Still write deterministic Markdown, checks, samples, and chart assets when Quarto is not available.
- Avoid relying on external network resources.

## Out of Scope

- Clustering charts or cluster interpretation.
- Full dashboard design.
- Live API reporting beyond showing already-generated API artifacts if present.
- Maximo maintenance overlays.
- Heavy plotting frameworks that make installation brittle.
- Notebook execution as the primary implementation path.

## Test Out Plan

- Run `uv run pytest`.
- Test report generation after the mock trend workflow or equivalent core commands.
- Test report output directory contains `report.md`, `checks.json`, `samples/`, and `charts/`.
- Test `checks.json` contains pass/fail records for each known mock behavior.
- Test chart files are written and non-empty.
- Test the report command handles missing trend artifacts with a clear message.
- Test Quarto absence does not fail the report generation path.
