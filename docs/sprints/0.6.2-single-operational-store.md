# Sprint 0.6.2 - Single Operational Store

## Problem Statement

Daily snapshots currently exist in three forms:

1. `sensor_snapshot.csv`;
2. a complete JSON object in `sensor_daily_snapshots.snapshot_json`;
3. dynamically added typed columns in the same SQLite row.

Routine trend artifacts, feature matrices, and metadata files add more copies.
Meanwhile, the live workflow loads high-frequency raw observations into SQLite,
builds a daily snapshot, verifies it, and then normally deletes those native rows.
The temporary store adds schema and orchestration without serving the web app after
the workflow completes.

This sprint makes the write path match the `0.6.1` read authority. Operational data
is stored once in a fixed SQLite schema. Files become temporary evidence or
explicitly requested exports.

## Working Decisions

### Use fixed typed daily columns

The operational snapshot table uses an explicit schema for the current identifier
and metric fields. It does not store a duplicate full-row JSON document and does not
alter its columns at runtime.

Schema changes are deliberate versioned migrations.

### Aggregate validated raw data directly

The normal sync path is:

```text
fetch temporary raw
  -> validate and checksum
  -> calculate daily rows
  -> transactionally upsert references, snapshots, events, and ledger
  -> verify durable facts
  -> release temporary raw according to policy
```

High-frequency observations do not need to be copied into persistent SQLite staging
before daily aggregation. A retained-raw/debug mode remains available for source
shape investigations.

### Files are exports, not coordination state

Snapshot, trend, feature, model, and report files are not written during a normal
sync merely so another core module can read them. Export functions query the
operational store and write a requested destination.

### One configured source per service instance

The database may retain `source` in primary keys for migration safety and provenance,
but a running web service uses its configured source. Mock and API instances use
separate data directories. Simultaneous mock/live comparison is not a browser
requirement.

## Requirements

1. Define a versioned, fixed daily snapshot schema containing the identifiers and
   metric fields used by the web and active registered models.
2. Migrate existing `sensor_daily_snapshots` rows into the fixed representation.
3. Verify migrated date, source, sensor, null, zero, and metric values before route
   cutover.
4. Remove `snapshot_json`, `snapshot_csv_path`, and runtime `ALTER TABLE` behavior
   from new writes.
5. Make the durable-fact transaction atomic per source/date: references, events,
   snapshot rows, and ingestion status either complete together or remain
   incomplete.
6. Add explicit ingestion-run states such as `started`, `validated`, `stored`,
   `models_pending`, `complete`, and `failed`.
7. Build daily snapshots directly from validated raw payloads without persistent
   native-observation staging.
8. Preserve compact references and action items while releasing only temporary raw
   and high-frequency data.
9. Stop normal snapshot and trend CSV/metadata writes.
10. Add store-backed snapshot and trend export functions with explicit destination
    paths.
11. Ensure rerunning a date is idempotent and safely replaces that date's durable
    facts in one transaction.
12. Add a snapshot data revision used to determine whether a registered model is
    current.
13. Reject startup when the configured source conflicts with an incompletely
    migrated data directory.

## In Scope

- Fixed daily snapshot schema and migration.
- Direct validated-raw aggregation.
- Atomic durable-fact persistence.
- Ingestion run state.
- Removal of routine snapshot/trend artifact writes.
- Snapshot and trend export boundary.
- One-source-per-service configuration.

## Out of Scope

- Removing existing historical artifact directories.
- Dropping all legacy SQLite staging tables.
- Changing clustering algorithms.
- Removing legacy cluster CLI commands.
- Browser navigation changes.
- Scheduling and deployment automation.

## Migration and Rollback

1. Create the new fixed table beside the existing snapshot table.
2. Copy and verify all existing rows.
3. Run repository parity and response-budget tests against the new table.
4. Switch operational reads and new writes.
5. Retain the old table and files, read-only, until `0.6.6`.
6. Record the migration version and row-count/hash audit in SQLite.

Rollback switches the repository configuration to the old table. It must not
require rebuilding source data during this sprint.

## Acceptance Criteria

1. A newly synchronized date has one operational daily snapshot representation.
2. Normal synchronization writes no snapshot or trend CSV/metadata artifact.
3. The fixed table contains no complete duplicate row JSON and requires no dynamic
   column alteration.
4. A failed sync cannot expose a partially updated date as ready.
5. Rerunning a date produces the same durable facts without duplicate events or
   references.
6. Snapshot and trend CSVs can still be produced through explicit export.
7. Mock tests use a separate configured data directory and do not require a browser
   source selector.
8. Existing dates preserve their values and sparse-data semantics after migration.

## Test Out Plan

- Run `uv run pytest`.
- Add migration tests from the current schema and from an empty database.
- Compare every migrated mock snapshot field against its pre-migration value.
- Test transaction rollback after validation, reference, event, and snapshot
  failure points.
- Test idempotent forced rebuilds.
- Verify routine sync creates no processed artifact files.
- Verify explicit export produces stable CSV columns and counts.
- Measure database size before and after the duplicate JSON representation is
  removed.
