# Sprint 0.4.1 - Navigation and Parameter Model

## Problem Statement

Sprint `0.4.0` made processed artifacts visible through FastAPI and a barebones static web app, but the browser controls are still too flat. Source, date range, equipment, sensor, dimension, and `k` appear as peer controls even though they operate at different levels of meaning.

This sprint should reshape the web app around a clear navigation and parameter model. Parameters are not just filters; they are the app's operating context. The UI should make it obvious which selections affect all tabs, which selections define the equipment/sensor scope, and which selections are view-specific details.

## Parameter Tiers

### Tier 1 - Global Context

These selections affect every tab:

```text
source
start_date
end_date
```

The global context defines the working universe. All artifact discovery, equipment browsing, trend loading, cluster loading, and drift/window loading should be interpreted inside this context.

### Tier 2 - Equipment and Sensor Scope

These selections define what the user is inspecting operationally:

```text
equipment_id
customer_asset_id
installation_point_id
sensor_id
```

This tier should support the normal workflow: find equipment, inspect its sensors, then review trends and related views. It should not feel like selecting from one enormous flat dropdown.

### Tier 3 - View-Specific Detail

These selections belong to specific tabs or chart/detail modes:

```text
dimension: x, y, z, temperature
k
metric family: rms velocity, rms acceleration, temperature, impact
```

Dimension appears in both trending and clustering, but it does not mean exactly the same thing in both places. For trending it is a display/metric selector. For clustering it is part of the model identity.

## Requirements

1. Redesign the static app layout around a persistent global context bar, an equipment/sensor navigator, and view-local controls.
2. Move `source`, `start_date`, and `end_date` into the global context tier.
3. Add an equipment/sensor navigation panel with searchable equipment rows and a sensor list for the selected equipment.
4. Keep "all equipment" and "all sensors" as explicit states.
5. Keep dimension and `k` controls local to the views that need them.
6. Preserve the read-only API behavior from sprint `0.4.0`.
7. Keep selected state in the browser URL query string or hash so a view can be refreshed or shared locally.
8. Normalize state transitions: when `source` or date range changes, downstream equipment, sensor, cluster, and drift selections should reset only when they are no longer valid.
9. Add clear missing-artifact states that name the selected parameters and, when useful, show the matching CLI command shape.
10. Keep route handlers thin; any new discovery or state-shaping helpers belong in core modules or browser presentation code, not ad hoc route logic.

## Proposed Layout

```text
top:      app title, health/source status
global:   source | start date | end date | refresh
left:     equipment search, equipment list, selected equipment sensors
main:     tabs and tab-specific controls
content:  summary, chart, table/detail
```

The app should remain dense and operational. Avoid landing-page patterns, oversized hero content, decorative cards, and explanatory marketing copy.

## Proposed State Shape

The browser should maintain one explicit state object:

```json
{
  "source": "api",
  "startDate": "2026-07-24",
  "endDate": "2026-07-26",
  "view": "trend",
  "equipmentId": "12345",
  "installationPointId": "201300",
  "dimension": "x",
  "metric": "rms_vel",
  "k": 4
}
```

This state should be the only source of truth for API calls. Controls update state; rendering reads state.

## API Expectations

The existing sprint `0.4.0` read endpoints should remain sufficient, but this sprint may add small discovery helpers if the current `/api/artifacts` and `/api/equipment` payloads make state management awkward.

Useful additions may include:

```text
GET /api/context?source=api&start_date=YYYY-MM-DD&end_date=YYYY-MM-DD
GET /api/equipment/{equipment_id}/sensors?source=api&start_date=YYYY-MM-DD&end_date=YYYY-MM-DD
```

Only add these if they simplify the UI materially. Do not add endpoints that compute clusters or fetch live source detail in this sprint.

## In Scope

- Global context bar.
- Equipment and sensor navigator.
- View-local dimension, metric, and `k` controls.
- URL-backed browser state.
- Better missing-artifact and invalid-selection states.
- Reuse of existing read-only API endpoints.
- Tests for static app structure and any new API discovery helpers.
- README or CLI docs update if local review workflow changes.

## Out of Scope

- Chart rendering overhaul beyond layout fixes needed for navigation.
- Home-grown SVG chart engine.
- API-triggered clustering.
- Live Waites source drilldown.
- Maximo maintenance history.
- Authentication and user profiles.
- Saved user defaults.

## Test Out Plan

- Run `uv run pytest`.
- Test static app includes global context controls, equipment navigator, view tabs, and view-local controls.
- Test any new discovery endpoints return stable JSON for fixture data.
- Test invalid source/date ranges return non-500 responses.
- Manually start `uv run sensor-data serve --source mock` and verify source/date/equipment/sensor changes drive the expected API requests.
- Verify the page remains usable on a narrow viewport.

## Next Sprint Lead In

Sprint `0.4.2` should focus on chart rendering and visual polish after the navigation model is stable. Do not spend this sprint perfecting chart internals while the state model is still moving.
