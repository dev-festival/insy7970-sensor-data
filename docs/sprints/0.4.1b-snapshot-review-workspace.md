# Sprint 0.4.1b - Snapshot Review Workspace

## Problem Statement

The equipment tree and scope behavior are now useful, but the Snapshot tab still behaves like an artifact inspection page. It shows summary counts, one broad chart, and a raw table, but it does not answer the normal review questions for a selected equipment or sensor:

```text
What am I looking at?
Which asset is it?
Which sensors are involved?
What changed over the selected date range?
Where does this sensor sit in cluster space?
Are there Waites action items or maintenance events to consider?
What are the actual daily measurement values?
```

This sprint turns Snapshot into the first equipment/sensor review workspace. It should stay barebones and data honest, but it should be laid out like the real operating surface rather than a generic chart demo.

## Working Decision

Build Snapshot as a composed review page for the selected scope.

The left navigator remains the source of truth for scope:

```text
all
asset_tree
equipment
sensor
```

The Snapshot tab should use the selected scope to render:

1. A context header.
2. A trend panel for selected sensors over the global date range.
3. A cluster-context panel for the selected date/feature-space/`k` when artifacts exist.
4. An action/event table using currently available Waites action items, with a Maximo-ready shape.
5. A measurement table using the daily snapshot rows.

The page should not call the live Waites API, mutate storage, or compute clusters at request time. It should read existing local artifacts and SQLite rows only.

## Primary User Flow

1. User selects `source`, `start_date`, and `end_date` globally.
2. User searches or expands the equipment tree.
3. User selects an equipment row or sensor row.
4. Snapshot renders a compact review page:

```text
Equipment Name       Asset Number       Rows of Data
Sensor Name or Sensor Count

[Trend panel over selected date range]
[Cluster map / drift context]
[Waites action item and future Maximo event table]
[Measurements table for the selected snapshot date]
```

For `all` or `asset_tree` scope, Snapshot should still render a useful summary state, but the primary detailed layout should be optimized for `equipment` and `sensor` scope.

## Date Behavior

Snapshot should no longer expose a prominent view-local date selector.

For this sprint, use the global `end_date` as the snapshot date when `state.date` is missing or out of range. Keep `date` in URL state for backward compatibility and artifact lookup, but visually treat Snapshot as part of the global date-range review.

Calendar-style global date inputs remain a separate follow-up unless this sprint needs to touch date controls anyway.

## Layout Contract

Snapshot should have its own DOM structure instead of reusing the generic summary-grid/plot/table stack.

Suggested anchors:

```html
<section id="snapshot-review" class="snapshot-review">
  <header id="snapshot-context" class="snapshot-context"></header>
  <section id="snapshot-trends" class="snapshot-panel"></section>
  <section id="snapshot-cluster-context" class="snapshot-panel"></section>
  <section id="snapshot-events" class="snapshot-panel"></section>
  <section id="snapshot-measurements" class="snapshot-panel"></section>
</section>
```

Non-snapshot tabs may continue to use the current generic chart/table surface until their own sprint work.

## Context Header

The context header should show different fields by scope.

For `sensor` scope:

```text
equipment_name
customer_asset_id
1 row of daily snapshot data
installation_point_name
```

For `equipment` scope:

```text
equipment_name
customer_asset_id
N rows of daily snapshot data
N sensors
```

For `asset_tree` or `all` scope:

```text
scope label
equipment count
sensor count
snapshot rows in scope
```

Avoid large marketing-style header treatment. This is an operations page: compact, scannable, and stable.

## Trend Panel

The trend panel should answer: "How did the selected sensor or equipment behave over the selected date range?"

Inputs:

```text
source
start_date
end_date
scope
metric
dimension when metric is axis-specific
aggregation/statistic
```

The first implementation may use the current metric selector and the `mean` aggregation. If adding aggregation is small, support:

```text
mean
max
min
std
```

Rendering expectations:

1. For `sensor` scope, show one line for the selected installation point.
2. For `equipment` scope, show small multiples or multiple muted lines for its sensors.
3. For broad scopes, show an equipment-level aggregate or a clear prompt to select equipment/sensor.
4. Prefer readable labels over raw IDs.
5. If trend artifacts are missing, show a compact empty state with the build command.

The chart engine decision remains part of `0.4.2`. This sprint may continue using Plotly if it is the fastest path, but the markup should not make Plotly mandatory forever.

## Cluster Context Panel

The cluster context panel should answer: "Where does the selected sensor or equipment sit in the cluster map for the current snapshot date?"

Inputs:

```text
source
snapshot date
feature_space
k
scope
```

Behavior:

1. Read existing cluster artifacts only.
2. Do not compute or persist clusters at request time.
3. Show the PCA/cluster map if the artifact exists.
4. Highlight selected sensor rows when `sensor` or `equipment` scope is active.
5. For missing artifacts, show a quiet unavailable state instead of letting Snapshot feel broken.

Cluster model registry and SQLite-backed cluster reads remain parked for `0.4.3`.

## Events Panel

The events panel should answer: "Are there open source-side action items or maintenance events tied to this asset/sensor?"

Use this source order:

1. Waites action items already present in local raw or SQLite data.
2. Future Maximo maintenance records once `0.5.0` lands.

The visible table can use a source-neutral shape:

```text
date
source
status
type
asset number
sensor / installation point
work order or action item id
title
```

In this sprint, it is acceptable for Maximo rows to be empty or unavailable. Do not implement live DB2/ODBC Maximo access in `0.4.1b`.

## Measurements Table

Replace the broad raw snapshot table with a compact daily measurements table for the selected scope.

Rows:

```text
one row per selected installation point / sensor
```

Recommended columns:

```text
sensor name
installation point id
asset number
rms velocity x/y/z mean
rms acceleration x/y/z mean
impact mean
temperature mean
selected metric max/min/std when useful
```

The first visible table should prioritize the selected metric family and avoid horizontal sprawl. Additional fields can remain available later through detail expansion or export.

```text

```

Query parameters:

```text
source
start_date
end_date
scope
asset_tree_id
equipment_id
installation_point_id
sensor_id
metric
dimension
feature_space
stat
```

## Browser Behavior

Snapshot rendering should be isolated behind a small set of functions, for example:

```text
renderSnapshotReview()
renderSnapshotContext()
renderSnapshotTrendPanel()
renderSnapshotClusterPanel()
renderSnapshotEventsPanel()
renderSnapshotMeasurements()
```

The existing generic functions can stay for Trend, Cluster, and Drift. Snapshot should not keep forcing its page into `summary-grid`, `plot`, and the generic `data-table` if that layout no longer matches the work.

## Empty States

Empty states should be specific and small:

```text
No snapshot rows for this scope.
No trend artifact for this range.
No cluster artifact for this date/feature space/k.
No action items found for this scope.
Select equipment or a sensor for detailed snapshot review.
```

Do not use large explanatory cards or visible instructions that crowd the review surface.

## In Scope

- Snapshot-specific page structure and styling.
- Context header for selected all/asset-tree/equipment/sensor scope.
- Snapshot date behavior aligned to the global date range.
- Scoped trend panel using existing trend artifacts.
- Cluster-context panel using existing cluster artifacts when available.
- Scoped Waites action item/event table if local data is available.
- Maximo-ready event table shape without implementing Maximo ODBC.
- Compact daily measurements table for selected scope.
- Tests for the snapshot review view model or composed API response.
- Static app smoke checks for Snapshot DOM anchors and rendering paths.

## Out of Scope

- Runtime cluster computation.
- Persisting new cluster artifacts from web requests.
- Live Waites drilldown for timestamp-level readings.
- Full Maximo DB2/ODBC integration.
- Calendar-style date picker replacement unless it is needed as a small supporting change.
- Redesigning Trend, Cluster, or Drift tabs beyond what Snapshot composition requires.
- Authentication, authorization, deployment, exports, and report scheduling.
