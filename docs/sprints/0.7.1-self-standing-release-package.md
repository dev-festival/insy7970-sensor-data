# Sprint 0.7.1 - Self-Standing Release Package

Status: Planned.

## Problem Statement

The `0.7.0` release can be developed and evaluated from a repository checkout, but
its release artifacts do not yet provide one consistent, self-standing package
experience. The installed wheel loads the default mock data from
`tests/fixtures`, a repository-only path that is absent from the wheel. The current
source archive also predates the addition of Ruff to the development dependency
group, so its documented quality checks cannot be reproduced from that archive.

The release README explains repository setup and mock operation, but it does not
distinguish installing the wheel from evaluating the extracted source archive. It
also does not provide one bounded release-verification sequence covering style,
tests, artifact construction, artifact contents, and an installed-wheel smoke test.

The project needs a patch release whose tag, source, README, wheel, and source
archive agree and contain everything required to install, run, and evaluate the
project and package without relying on an untagged checkout.

## Working Decisions

### Runtime mock data belongs to the package

The deterministic Waites and Maximo mock JSON used by normal mock-mode operation is
runtime package data, not test-only data. Move the canonical runtime fixtures under
`src/insy_sensor_data/fixtures/`, preserving the existing `waites/` and `maximo/`
subdirectories and controlled dates.

Default fixture discovery must resolve the installed package-owned directory. It
must not derive runtime data paths from the repository root or require a sibling
`tests/` directory. Explicit `fixture_dir` overrides remain supported for focused
tests and callers that deliberately supply alternate fixtures.

Hatchling configuration must include all runtime fixture JSON in the wheel and
source distribution. Artifact inspection is part of acceptance; a successful
repository test run alone does not prove package completeness.

### Tests and runtime fixtures have separate roles

The package-owned fixtures are the canonical offline demonstration dataset. Tests
may consume those fixtures through the same package boundary or retain narrowly
scoped test-only data under `tests/fixtures`, but they must not be the source of
runtime files required by an installed wheel. Duplicate canonical fixture trees
that can drift independently are not acceptable.

### The source archive is the project evaluation artifact

The extracted source archive contains the lockfile, development dependency group,
tests, scripts, documentation, and package source needed to reproduce repository
checks. Ruff must be locked in the development dependency group before the release
artifacts are built.

The wheel is the installation artifact. It must support the documented offline
mock initialization and service startup from a clean directory that has no access
to the repository source tree.

### The README defines distinct release paths

Update the project README with a concise release-artifact section that clearly
separates:

1. installing and smoke-testing the attached wheel;
2. extracting, synchronizing, and evaluating the attached source archive; and
3. running the deterministic offline mock demonstration.

The README must name Python 3.13 or newer and `uv` as prerequisites, show how to
create the mock `.env`, and state that mock evaluation requires no Waites token,
ODBC driver, DB2 connection, or plant network. Commands must be complete enough to
run from the documented starting directory without relying on unstated repository
knowledge.

The source-evaluation path must include the locked environment and required gates:

```powershell
uv sync --locked --dev
uv run ruff check .
uv run pytest
uv build --no-sources
```

The wheel path must install the named `0.7.1` wheel into a clean environment and
exercise at least CLI discovery, mock synchronization for the controlled date
range, service health, and one representative application read. The README should
describe the source archive as the route for running the complete test suite and
rebuilding package evidence.

### Release artifacts are derived from the tagged commit

The final wheel and source archive must be built from the clean commit that receives
the `0.7.1` tag. Artifact filenames and package metadata must report version
`0.7.1`. The two files attached to the GitHub Release must be the files produced by:

```powershell
uv build --no-sources
```

Do not reuse or rename `0.7.0` artifacts. Record SHA-256 checksums before upload so
the attached files can be compared with the locally verified files. The release
page, tag, README, wheel metadata, source archive metadata, and checksums must refer
to the same source state.

## Requirements

1. Move the canonical Waites and Maximo runtime mock fixtures into the
   `insy_sensor_data` package tree.
2. Resolve default mock fixtures from installed package resources rather than
   `PROJECT_ROOT/tests/fixtures`.
3. Preserve explicit fixture-directory overrides used by tests and internal
   boundaries.
4. Configure and verify Hatchling packaging so every required runtime JSON fixture
   is present in both the wheel and source archive.
5. Keep tests, the lockfile, scripts, documentation, `.env.example`, and README in
   the source archive so it remains independently evaluable.
6. Include Ruff in the locked development dependency group and make
   `scripts/check.sh` reproducible after `uv sync --locked --dev`.
7. Update the project version and generated artifact metadata to `0.7.1`.
8. Update the README with separate wheel installation, source evaluation, mock
   initialization, run, and verification instructions.
9. Verify the wheel from a clean directory outside the repository, with no source
   checkout available through the working directory or import path.
10. Build the final wheel and source archive with `uv build --no-sources` from the
    exact clean commit that is tagged and released.

## In Scope

- Runtime fixture ownership and installed-package resource discovery.
- Hatchling wheel and source-archive inclusion rules.
- Tests that detect missing installed-package fixture data.
- Ruff development dependency and lockfile consistency.
- Package version `0.7.1`.
- README release installation, operation, and evaluation instructions.
- Clean-environment artifact inspection, installation, mock smoke testing, and
  checksums.

## Out of Scope

- Changes to mock fixture values, controlled dates, trend overlays, or expected
  domain behavior.
- New Waites or Maximo endpoints, schemas, service features, or browser workflows.
- Changes to live credentials, DSNs, scheduling, retention, or operational data.
- Publishing to PyPI or another package registry.
- Bundling Python, `uv`, DB2 drivers, live credentials, or external service data in
  the release.
- Treating repository-only test helpers as supported runtime package APIs.

## Compatibility Gate

Mock-mode behavior, CLI commands, API responses, controlled dates, and live-source
boundaries remain unchanged. Existing callers that pass an explicit `fixture_dir`
must continue to work. The patch changes where default runtime fixture files are
owned and discovered; it must not change their data contract or generated durable
facts.

## Acceptance Criteria

1. Listing the `0.7.1` wheel shows all canonical Waites and Maximo runtime JSON
   beneath the installed `insy_sensor_data` package.
2. The `0.7.1` source archive contains the README, `.env.example`, `pyproject.toml`,
   `uv.lock`, tests, test fixtures or overrides, scripts, docs, package source, and
   package-owned runtime fixtures.
3. In a clean directory outside the repository, installing only the wheel and its
   declared dependencies permits `sensor-data --help` and `sensor-data doctor
   --json` to run.
4. In that clean installation, the README's mock configuration can synchronize
   2025-07-09 through 2025-07-11, start the service, return a healthy `/health`
   response, and serve a representative snapshot or trend request without external
   credentials or repository files.
5. From an extracted source archive, `uv sync --locked --dev`, Ruff, and the complete
   non-live test suite succeed using only the archive and dependency indexes.
6. `scripts/check.sh` no longer fails because Ruff is absent after the documented
   locked development synchronization.
7. `uv build --no-sources` creates exactly one `0.7.1` wheel and one `0.7.1` source
   archive whose package metadata, included README, and source agree.
8. The README contains complete, distinct instructions for wheel installation,
   source-archive evaluation, offline mock initialization, service startup, and
   artifact rebuilding.
9. SHA-256 checksums recorded immediately before upload match both assets attached
   to the GitHub Release linked in the project reflection.
10. The release tag identifies the exact clean commit used to build and verify the
    uploaded artifacts.

## Test Out Plan

- Retain focused tests for explicit `fixture_dir` overrides and invalid/missing
  fixture failures.
- Build with `uv build --no-sources` and inspect both archives for the required

- Extract the source archive into a fresh temporary directory; run
  `uv sync --locked --dev`, `uv run ruff check .`, and `uv run pytest` there.
- Create a separate clean environment and working directory, install only the built
  wheel, create the documented mock configuration, and run CLI, synchronization,
  health, and representative API smoke checks.
- Ensure the clean wheel test does not set `PYTHONPATH`, run from the repository, or
  otherwise expose repository fixtures.
- Confirm package and artifact versions are `0.7.1`, calculate SHA-256 checksums,
  and compare those exact local artifacts with the GitHub Release assets.

## Release Sequence

The sprint follows this ordered evidence boundary:

```text
specification commit
  -> implementation and README commit
  -> clean full verification
  -> 0.7.1 tag on the verified commit
  -> uv build --no-sources from that tag
  -> checksum and artifact inspection
  -> GitHub Release with both exact artifacts attached
```

Do not tag or upload artifacts while implementation, README, lockfile, or version
changes remain uncommitted.
