# Sprint 0.2.9 - Daily Snapshot Store and Raw Release

## Problem Statement

The current live workflow still treats raw endpoint JSON and timestamp-native SQLite observations as the durable working layer. That was useful while proving live shape and replay behavior, but it is not the right default before clustering. The durable operating fact should be the daily sensor snapshot: one row per sensor/installation point with daily min, mean, and max fields for vibration, temperature, and other selected measurements.

This sprint shifts the default pipeline posture from "keep raw evidence unless manually packed later" to "prove the pull, preserve a small ledger, write durable daily facts, and release bulky raw/native evidence unless explicitly retained for inspection."

## Requirements

1. Add a durable SQLite snapshot store that contains the same daily snapshot facts written to `sensor_snapshot.csv`.
2. Keep the CSV snapshot as the portable artifact and make the SQLite snapshot the queryable downstream working table.
3. Add an ingestion ledger that survives raw release and records source, date, facility, endpoint row counts, validation status, raw artifact checksums, snapshot row count, and retention action.
4. Add raw retention modes to workflow commands: `release`, `compress`, and `keep`.
5. Make live workflow defaults use `release` after validation and snapshot success. Mock workflows may keep raw by default for fixture inspection unless tests are updated to cover release mode.
6. Add an explicit option to retain raw/native evidence for troubleshooting live shape problems.
7. Add a command to purge timestamp-native SQLite observation rows after daily snapshots and ledger records exist.
8. Ensure trend, feature, report, and future clustering paths can consume the SQLite snapshot store or the snapshot CSV without requiring raw endpoint JSON or native observation rows.
9. Preserve rerun safety: release must not delete raw or native rows until the ledger and daily snapshot store are verified for that date.
10. Document the new operating path and the inspection/replay escape hatch.

## In Scope

- SQLite daily snapshot table or tables.
- Snapshot build writes both CSV and SQLite daily facts.
- Lightweight ingestion ledger.
- Workflow retention mode options.
- Raw release after successful validation and snapshot persistence.
- Native observation purge for dates whose daily snapshot is stored.
- Tests over mock data proving raw/native release does not break snapshot, trend, feature preview, or report generation.
- Documentation for live three-day canary workflow with snapshot-only retention.

## Proposed SQLite Shape

The first implementation can use a wide daily snapshot table that mirrors `sensor_snapshot.csv` because it keeps the current snapshot and feature contracts stable:

```text
sensor_daily_snapshots
  source
  source_date
  installation_point_id
  installation_point_name
  equipment_id
  equipment_name
  sensor_id
  facility_id
  customer_asset_id
  installation_customer_asset_id
  equipment_customer_asset_id
  impact_min
  impact_mean
  impact_max
  rms_accel_min_x
  rms_accel_mean_x
  rms_accel_max_x
  ...
  temp_sensor_min
  temp_sensor_mean
  temp_sensor_max
  temp_ambient_min
  temp_ambient_mean
  temp_ambient_max
  built_at
  snapshot_csv_path
  PRIMARY KEY (source, source_date, installation_point_id)
```

A later normalized view/table can be added if feature queries become awkward:

```text
sensor_daily_metrics
  source
  source_date
  installation_point_id
  measurement
  dimension
  statistic
  value
```

Do not make the normalized table a prerequisite for this sprint unless the wide-table implementation blocks downstream work.

## Ingestion Ledger

The ledger should make it possible to prove what happened without keeping bulky evidence:

```text
waites_ingestion_ledger
  source
  source_date
  facility_id
  fetched_at
  validated_at
  snapshot_built_at
  validation_status
  validation_error_count
  validation_warning_count
  endpoint_counts_json
  endpoint_artifacts_json
  manifest_sha256
  snapshot_row_count
  snapshot_store_status
  raw_retention_mode
  raw_retention_status
  native_retention_status
```

`endpoint_artifacts_json` should include logical path, byte count, SHA-256, and compressed metadata when available. It should not require the raw files to still exist.

## Retention Modes

```text
release
compress
keep
```

- `release`: after validation and successful snapshot CSV + SQLite persistence, delete raw endpoint payload files and timestamp-native SQLite observation rows for the date. Keep manifest, validation report, ledger, snapshot CSV, and SQLite daily snapshot facts.
- `compress`: after validation and successful snapshot persistence, gzip raw endpoint payload files and keep native SQLite observation rows unless a separate native purge option is requested.
- `keep`: preserve raw endpoint payload files and native SQLite observation rows for inspection and replay.

Destructive release behavior must be scoped to an explicit source/date/facility and should refuse to run if snapshot persistence is missing or validation failed.

## Suggested Commands

The exact names can settle during implementation, but the user-facing shape should be close to:

```powershell
uv run sensor-data workflow api-day --date 2026-07-13 --facility 679 --raw-retention release
uv run sensor-data workflow api-range --start-date 2026-07-13 --end-date 2026-07-15 --facility 679 --raw-retention release
uv run sensor-data snapshot store --source api --date 2026-07-13
uv run sensor-data store purge-native --source api --date 2026-07-13 --confirm-delete
uv run sensor-data store purge-native --source api --start-date 2026-07-13 --end-date 2026-07-15 --confirm-delete
```

Useful options:

```powershell
--raw-retention release|compress|keep
--keep-native
--json
--dry-run
--confirm-delete
```

## Default Operating Path

For live data, the intended default after this sprint is:

```text
fetch raw endpoint payloads for one date
validate raw shape
record ingestion ledger
build daily snapshot CSV
store daily snapshot in SQLite
verify snapshot persistence
release raw endpoint payloads
purge timestamp-native SQLite observation rows unless inspection retention is requested
```

Trend, feature preview, clustering, drift, and reporting should consume the daily snapshot store or snapshot CSV, not raw JSON and not timestamp-native observation tables.

## Out of Scope

- Changing the daily snapshot metric contract from the current min/mean/max/std fields.
- Changing the clustering feature contract from sprint `0.2.8`.
- Full production scheduler.
- Cloud/object storage retention policy.
- Automatic deletion across broad date ranges without explicit date/range scope.
- Removing the lower-level raw fetch, validate, compress, or load commands.

## Test Out Plan

- Run `uv run pytest`.
- Test snapshot build writes both CSV and SQLite daily snapshot rows.
- Test trend and feature preview can read from snapshot CSV after native observation rows are purged.
- Test the SQLite snapshot store has the same row count and key fields as `sensor_snapshot.csv`.
- Test ingestion ledger persists endpoint counts, validation status, manifest hash, snapshot row count, and retention status.
- Test `release` refuses to delete raw/native evidence before a successful snapshot CSV and SQLite snapshot record exist.
- Test `release` deletes raw endpoint payload files for one date while preserving manifest, validation report, ledger, and snapshot artifacts.
- Test native purge deletes timestamp-level RMS, temperature, ImpactVue, and action-item rows without deleting daily snapshots or ledger rows.
- Test `keep` preserves raw and native observations for inspection.
- Test `compress` preserves readable compressed raw artifacts.

## Next Sprint Lead In

Sprint `0.3.0` can then run clustering against durable daily facts instead of carrying raw evidence or timestamp-native observation rows as implicit dependencies. Sprint `0.3.1` can focus on date-window orchestration over a pipeline whose per-date storage posture is already clear.
