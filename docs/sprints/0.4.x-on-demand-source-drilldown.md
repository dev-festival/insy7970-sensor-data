# Sprint 0.4.x - On-Demand Source Drilldown

## Problem Statement

The dashboard should not require locally storing every timestamp-level Waites reading just in case a user wants to inspect one point later. The durable local layer should stay small: daily snapshots, SQLite-backed trend views, registered cluster models, drift outputs, reports, and an ingestion ledger. When a daily fact needs more attention, the dashboard can perform a narrow live pull back to Waites for the exact source date, equipment/sensor, measurement, and dimension.

This sprint adds an on-demand drilldown path: a user can click a suspicious daily point, fetch the source-detail readings for that point, render a temporary high-resolution chart, and discard the detail unless explicitly retained for inspection.

## Requirements

1. Add a dashboard drilldown interaction from a daily snapshot, trend, cluster, or drift point.
2. Use existing daily facts and ingestion ledger rows to construct a narrow source request: source date, facility, installation point or sensor, metric family, and dimension/axis where relevant.
3. Fetch only the source readings needed for the selected point, not a full-day/full-facility payload when the source API supports narrower filtering.
4. Validate the returned detail shape before rendering it.
5. Render a high-resolution temporary chart for the selected measurement, such as one day of X-axis RMS readings for one sensor.
6. Do not persist raw drilldown readings by default.
7. Allow explicit operator retention for troubleshooting, with the same manifest, validation, and ledger discipline used by normal ingestion.
8. Keep dashboard and FastAPI route handlers thin; source request construction, validation, optional caching, and chart data shaping belong in core modules.
9. Make the feature work in mock mode with deterministic fixture-backed detail responses.
10. Add clear UI states for unavailable source credentials, source API failure, no readings returned, validation warnings, and retained-versus-temporary detail.

## In Scope

- Read-only dashboard drilldown from daily fact views.
- FastAPI endpoint for source-detail requests.
- Core Waites source-detail fetch helper.
- Temporary in-memory or short-lived file cache for repeated clicks during a session.
- Mock source-detail fixture path.
- High-resolution chart data shaping for RMS, temperature, and other supported measurement families.
- Optional explicit "retain this detail" path for troubleshooting.
- Tests for API response shape, source request scoping, mock detail rendering data, validation failures, and non-persistence by default.

## Out of Scope

- Reintroducing timestamp-native readings as the default local storage layer.
- Automatic background backfills of high-resolution readings.
- Long-lived local drilldown cache by default.
- Clustering on drilldown readings.
- Maximo drilldown beyond linking the selected equipment context.
- Authentication or role-based permissions unless the dashboard hardening sprint has already introduced them.

## Proposed User Flow

```text
user opens dashboard daily trend or cluster view
user selects Equipment A / Sensor 1 / 2026-07-15 / X-axis RMS
dashboard asks FastAPI for source detail
FastAPI checks local daily snapshot and ingestion ledger context
core Waites client performs narrow live pull
response is validated and shaped into chart-ready points
dashboard renders timestamp-level detail for inspection
detail is discarded after the session unless explicitly retained
```

## Proposed API Shape

The exact endpoint can settle during implementation, but the intended shape is:

```text
GET /api/source-detail/waites
  ?date=YYYY-MM-DD
  &facility=679
  &installation_point_id=201300
  &measurement=rms.velocity
  &dimension=x
```

Response:

```json
{
  "source": "api",
  "date": "2026-07-15",
  "facility_id": 679,
  "installation_point_id": "201300",
  "measurement": "rms.velocity",
  "dimension": "x",
  "retention": "temporary",
  "validation_status": "valid",
  "point_count": 96,
  "points": [
    {"timestamp": "2026-07-15T00:15:00Z", "value": 0.071}
  ],
  "source_request": {
    "endpoint": "readings-rms",
    "scope": "single installation point, single axis, single date"
  }
}
```

The response should avoid returning unrelated source payload fields. The dashboard only needs timestamp, value, units, validation status, and enough source context to explain what it is showing.

## Retention Policy

Default behavior:

```text
temporary
```

Temporary detail may live in memory or a short-lived cache directory for the current server session. It should not be treated as durable project state.

Explicit retention behavior:

```text
retain
```

Retained detail should write:

```text
data/raw/waites/detail/
  date=YYYY-MM-DD_installation=ID_measurement=VALUE_dimension=VALUE/
    readings.json or readings.json.gz
    manifest.json
    validation.json
```

Retained detail must be deliberate, auditable, and safe to prune later. It should not silently bypass the raw-release policy from sprint `0.2.9`.

## Safety and Permissions

- Missing `WAITES_ACCESS_TOKEN` should return a clear dashboard/API error, not a server crash.
- The dashboard should show when it is displaying live source detail versus durable local daily facts.
- Drilldown should rate-limit or debounce repeated clicks so the dashboard does not accidentally hammer the source API.
- Detail requests should be narrow and explainable in logs.
- Source credentials must never be returned to the browser or written to retained detail artifacts.

## Test Out Plan

- Run `uv run pytest`.
- Test mock drilldown returns deterministic timestamp-level points for one sensor/date/measurement/dimension.
- Test live drilldown route fails clearly when credentials are unavailable.
- Test request validation rejects unsupported measurement families or dimensions.
- Test default drilldown does not write raw detail artifacts.
- Test explicit retain mode writes manifest, validation, and detail artifacts under a scoped detail directory.
- Test dashboard-facing response includes point count, validation status, units/context, and chart-ready points.
- Test detail request construction uses the narrowest supported Waites filters.

## Next Sprint Lead In

This sprint keeps the dashboard powerful without bloating local storage. Daily snapshots remain the durable operating layer, clustering remains based on compact daily facts, and high-resolution source data is pulled only when a human asks a specific question.
