# Sprint 0.6.6 - Legacy Retirement and Release Hardening

## Problem Statement

The preceding reshaping sprints deliberately retain old files, tables, loaders, and
command aliases while new paths prove parity. Leaving that compatibility layer in
place indefinitely would recreate the same ambiguity the phase is intended to
remove.

This sprint performs the controlled retirement. It removes unused artifact flows,
old schema copies, legacy clustering orchestration, report scaffolding without a
confirmed consumer, and deprecated CLI aliases. It also packages migration,
rollback, operating, and deployment evidence for the reshaped service.

Cleanup is potentially destructive and must be recoverable.

## Working Decisions

### Retirement requires evidence

A legacy path is removed only when:

- no normal web route imports or reads it;
- no new public CLI command depends on it;
- parity or intentional replacement is documented;
- the current data store has passed migration audits;
- rollback material exists.

### Cleanup is manifest-driven

The cleanup operation inventories exact targets, sizes, and checksums. It defaults
to dry run, creates or verifies a backup/archive destination, and requires explicit
confirmation before removing data.

No recursive cleanup targets the project root, `data/`, or an unresolved path.

### Reports need a named consumer

The mock Quarto/evidence-report subsystem is removed unless an external consumer is
recorded before this sprint. Required tabular data remains available through
`export`.

### Documentation describes the system that remains

The Grand Design, README, CLI guide, data contract, and service operations must stop
describing artifacts and the CLI as the primary application architecture.

## Requirements

1. Remove normal snapshot, trend, reference, event, cluster, drift, and readiness
   file fallback code.
2. Remove legacy dimension-oriented feature/cluster/drift/window orchestration after
   extracting any active engine helpers.
3. Remove routine feature, snapshot, trend, cluster-model, and drift artifact
   writers.
4. Remove deprecated CLI command aliases and obsolete workflow formatting code.
5. Remove the evidence-report/Quarto subsystem if no named consumer is documented.
6. Migrate SQLite to remove duplicate snapshot JSON/path columns and obsolete
   native-staging or legacy-model tables that are no longer used.
7. Vacuum or rebuild the SQLite database only after verified migration and backup.
8. Provide a dry-run-first cleanup command or script that inventories historical
   derived artifact targets and never touches raw evidence without a separate
   explicit policy.
9. Record cleanup counts, bytes, checksums/manifest, backup location, and completion
   status.
10. Update `README.md`, `docs/GRAND_DESIGN.md`, `docs/CLI.md`, and relevant data
    contracts for the web-first architecture.
11. Archive superseded sprint specifications where doing so improves roadmap
    readability without erasing history.
12. Add deployment/startup notes, schema migration steps, backup/restore steps, and
    routine sync/doctor examples.
13. Establish final code, response-size, data-file, and startup/query baselines.
14. Perform a clean-store rehearsal and an in-place migration rehearsal.

## Expected Retirement Candidates

```text
data/processed/snapshots/
data/processed/trends/
data/processed/features/
data/processed/clusters/
data/processed/drift/
data/processed/cluster_windows/
data/processed/cluster_models/
data/processed/cluster_model_drift/
```

These are candidates, not unconditional deletion targets. Explicit exports or
externally consumed files must be relocated and documented before cleanup.

Code candidates include:

- artifact discovery/load fallbacks;
- legacy cluster/window file orchestration;
- mock evidence report generation;
- old workflow command wrappers and emitters;
- dynamic snapshot schema and duplicate JSON logic;
- native staging loaders retained only for the former release workflow.

## In Scope

- Code retirement.
- Versioned database cleanup.
- Recoverable historical artifact cleanup.
- Documentation realignment.
- Migration, rollback, and operational release evidence.
- Final performance and footprint baselines.

## Out of Scope

- Deleting raw source evidence under a new retention policy.
- Authentication, profiles, or authorization.
- Scheduled execution.
- New analytics or chart types.
- Changing Maximo query semantics.
- Production infrastructure provisioning.

## Destructive-Action Gate

Before deleting material data:

1. resolve and print absolute target paths;
2. verify each target is within the configured processed-data directory;
3. create a manifest with file size and checksum;
4. verify a backup/archive destination outside the deletion target;
5. run read/API parity against the SQLite operational store;
6. run cleanup in dry-run mode;
7. require explicit confirmation;
8. rerun service and database audits after cleanup.

Rollback instructions must restore both the database and any externally required
exports.

## Acceptance Criteria

1. Normal service startup and requests do not inspect legacy processed artifact
   directories.
2. The public CLI contains no deprecated command families.
3. The active clustering path has one engine, one persistence path, and one model
   policy.
4. The operational snapshot row has one fixed representation.
5. Cleanup dry run lists only validated processed-artifact targets.
6. Confirmed cleanup has a recoverable manifest and backup.
7. README and Grand Design describe FastAPI/web as primary and CLI as supporting
   administration.
8. A clean data directory can sync, serve Review/Fleet Trends/Drift, rebuild, doctor,
   and export.
9. An existing `0.5.1` data directory can migrate to the same outcome.
10. Response-size budgets and sparse-data semantics remain satisfied after all
    compatibility code is removed.

## Test Out Plan

- Run the complete pytest suite.
- Run JavaScript syntax checks.
- Run clean-store and in-place migration rehearsals.
- Run backup, dry-run cleanup, confirmed cleanup, and restore rehearsals against a
  disposable copy.
- Verify Snapshot Review, Fleet Trends, Drift, Waites Events, and bounded Maximo
  behavior after artifacts are absent.
- Compare pre/post database row counts and representative metric values.
- Record processed file count, processed bytes, database bytes, default response
  sizes, and request timings.
- Confirm no test recreates a retired artifact as hidden coordination state.

## Reshaping Phase Definition of Done

The `0.6.x` phase is complete when:

- the web service reads one operational SQLite model;
- synchronization writes durable facts once;
- events survive normal retention;
- the browser receives compact server-scoped responses;
- one registered model pipeline serves cluster and drift views;
- the CLI exposes only administration, repair, diagnosis, and export;
- legacy storage and code are removed through a recoverable process;
- current architecture and operations are documented and tested.

## Next Sprint Lead In

After `0.6.6`, feature work can resume on a smaller base. Candidate `0.7.x` work may
include scheduling, deployment hardening, authentication/profiles, caching based on
measured need, or on-demand timestamp-level source drilldown. Those features should
not reopen parallel operational storage paths.
