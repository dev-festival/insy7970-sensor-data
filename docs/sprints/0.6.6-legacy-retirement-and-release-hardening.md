# Sprint 0.6.6 - Legacy Retirement and Release Hardening

Status: Checkpoint A implemented and rehearsed on 2026-08-02; Checkpoint B remains
unapproved and unexecuted.

Implementation evidence:

- [retirement inventory](../RETIREMENT_0_6_6.md)
- [benchmarks and schema-v8 rehearsal](../benchmarks/0.6.6-legacy-retirement.md)
- environment-specific live dry-run manifest under ignored `maintenance/`

## Problem Statement

Sprints `0.6.0` through `0.6.5` have already established the new operating path:

- normal web routes read the operational SQLite repositories;
- synchronization writes fixed daily facts and registered models without routine
  processed-file mirrors;
- the browser uses compact, service-owned source and model policy;
- the public CLI exposes `serve`, `sync`, `rebuild`, `doctor`, and `export`.

The compatibility layer intentionally retained while those paths proved parity is
still present. Hidden CLI families import old workflows, artifact discovery and
file loaders remain in the tree, legacy clustering can still write dimension-based
files, storage initialization still creates retired directories, and SQLite still
contains the duplicate snapshot representation and empty native-staging schema.

This sprint removes that dormant machinery without changing the web workflows that
made the service fast. It also packages a versioned migration, consistent backup,
restore rehearsal, cleanup manifest, operating instructions, and final reshaping
benchmarks.

Cleanup is potentially destructive. Implementation and rehearsal may proceed on
disposable copies, but changing material live data requires a separate explicit
approval of the exact manifest and backup.

## Measured Starting Point

The current API service store provides the primary in-place migration baseline:

- `data/processed/observations.sqlite` is 244,944,896 bytes;
- the schema is version 8 and the configured source is `api`;
- `sensor_daily_facts` is the verified authority with 18,436 API rows;
- legacy `sensor_daily_snapshots` contains the same 18,436 API keys plus nine old
  mock rows and approximately 44.7 million duplicate JSON/path characters;
- native RMS, impact, temperature, and daily-rollup staging tables contain zero
  rows;
- the eight original derived-artifact candidates contain 828 files and 85,535,749
  bytes;
- the old processed Waites reference mirror adds four files and 2,266,797 bytes.

These measurements are evidence for planning, not deletion authorization. They must
be remeasured when the cleanup manifest is generated.

## Working Decisions

### Retirement verifies the fast path already in place

A legacy path is removed only when:

- no normal web route imports, reads, or writes it;
- none of the five public CLI commands depends on it;
- any active pure helper or contract has been extracted first;
- parity or intentional replacement is documented;
- the current data store has passed migration audits;
- rollback material exists.

Tests written only for a retired interface do not make that interface operational.
They are replaced with tests of the surviving contract rather than preserving dead
production code for test compatibility.

### The public CLI remains five commands

Historical cleanup is implemented as a versioned maintenance script under
`scripts/`, not as a sixth public command. After this sprint, the top-level command
surface remains exactly:

```text
sensor-data serve
sensor-data sync
sensor-data rebuild
sensor-data doctor
sensor-data export
```

### Cleanup has two explicit checkpoints

Checkpoint A covers code retirement, schema implementation, disposable-copy
migration, backup/restore rehearsal, and a dry-run manifest against the configured
store. These actions do not delete material live data.

Checkpoint B covers confirmed deletion, live schema compaction, and database space
reclamation. It requires explicit operator approval that identifies the dry-run
manifest and verified backup. A general request to execute the sprint does not
implicitly authorize Checkpoint B.

### SQLite backup must be consistent

The service must be stopped or the administrative writer lease must exclude other
writers. Database backup uses SQLite's backup mechanism or another SQLite-consistent
method, not an ordinary copy of a live database file. The backup is stored outside
the cleanup targets, checksummed, checked for integrity, and restored during a
disposable rehearsal before live compaction.

### Active operational tables are protected

Every proposed table or column removal requires a live read/write reference audit.
The migration must preserve fixed daily facts, source/reference facts, event and
coverage facts, ingestion ledger and run transitions, snapshot revisions, current
registered model/drift tables, synchronization state, writer leases, administration
audit, and migration evidence.

In particular, `ingestion_runs` and `ingestion_run_transitions` are active parts of
direct durable ingestion; they are not native-staging leftovers. Current registered
model tables are also not retirement candidates merely because older rows contain
artifact-oriented columns.

### Source and model policy remain service-owned

The standalone Cluster tab and its registered model data remain first-class web
features. Retirement targets the old file/dimension orchestration and compatibility
parameters, not Cluster exploration or the future starmap direction.

Public web routes no longer accept browser-obsolete source, feature-space, or `k`
selection where the configured service source and active model policy already own
those choices. Maximo SQL/query meaning does not change.

### Reports need a named consumer

The mock Quarto/evidence-report subsystem is removed because no external consumer
has been recorded. Required tabular data remains available through `export`.
Benchmark Markdown is release evidence and is not part of the Quarto subsystem.

### Documentation and specifications preserve history

The Grand Design, README, CLI guide, data contract, and service operations describe
the web-first system that remains. Sprint specifications stay in Git and remain
linked from the sprint index; they are marked by status rather than moved merely to
reduce the active file list.

18. Reclaim database space only after verified migration and backup. Prefer a

## Expected Retirement Candidates

```text
data/processed/waites/reference/
data/processed/snapshots/
data/processed/trends/
data/processed/features/
data/processed/clusters/
data/processed/drift/
data/processed/cluster_windows/
data/processed/cluster_models/
data/processed/cluster_model_drift/
```

These are candidates, not unconditional deletion targets. Explicit exports or
externally consumed files must be relocated and documented before cleanup. Parent
directories are removed only when empty and individually validated. Neither
`data/`, `data/processed/`, the operational SQLite database, nor any unresolved path
is ever a recursive cleanup target.

Code candidates include:

- dormant `artifact_views` discovery and file loaders;
- legacy cluster feature/model/window file orchestration;
- mock evidence-report generation;
- hidden Typer groups, workflow wrappers, and emitters;
- processed snapshot/trend loaders and writers retained only for compatibility;
- unused processed-reference writers;
- obsolete storage path helpers and eager directory creation.

Database candidates include:

- the duplicate `sensor_daily_snapshots` table and its JSON/path representation;
- empty timestamp-native observation and daily-rollup staging tables after their
  legacy loaders are removed;
- obsolete indexes and non-active legacy model rows proven outside the registered
  policy.

Database candidates do not include active registered model/drift tables,
`sensor_daily_facts`, Waites references/events/coverage, ingestion audit state,
synchronization state, or administration audit/lease state.

## In Scope

- Dormant code and compatibility-interface retirement.
- Versioned, source-safe database cleanup.
- A dry-run manifest against the configured live store.
- Recoverable historical artifact cleanup after separate approval.
- Documentation and configuration realignment.
- Migration, rollback, startup, and operational release evidence.
- Final performance and footprint baselines.

## Out of Scope

- Deleting raw source evidence under a new retention policy.
- Implicitly authorizing Checkpoint B through a general sprint execution request.
- Authentication, profiles, or authorization.
- Provisioning Task Scheduler/cron jobs; the scheduler-ready `sync` contract from
  `0.6.5` must remain unchanged.
- New analytics, chart types, or changes to the standalone Cluster product surface.
- Changing Maximo SQL or query semantics.
- Production infrastructure provisioning.
- Moving or deleting historical sprint specifications.

## Destructive-Action Gate

Before deleting material files or compacting the live database:

1. stop the service or prove exclusive administrative writer ownership;
2. resolve and print every absolute target path;
3. verify each file target is within an individually allowed processed-artifact
   directory and that no target is raw evidence;
4. record pre-change database integrity, schema, source, row counts, representative
   values, response parity, and performance baselines;
5. create a SQLite-consistent database backup and any required artifact archive
   outside the deletion targets;
6. verify backup/archive checksums and database integrity;
7. restore the backup into a disposable location and rerun representative reads;
8. generate the dry-run cleanup manifest and checksum it;
9. require explicit approval naming that manifest and backup;
10. apply only the approved targets and migration;
11. verify database integrity and reclaim space through the recoverable compaction
    procedure;
12. rerun service, database, source-boundary, and performance audits;
13. record completion status, post-change counts/bytes, and rollback location.

Rollback instructions restore both the database and any externally required
exports. Any target or parity mismatch stops the cleanup without broadening the
manifest automatically.

## Acceptance Criteria

### Checkpoint A - release candidate and dry run

1. Normal service startup and requests neither inspect nor recreate legacy
   processed-artifact directories.
2. The public CLI contains exactly the five `0.6.5` commands and no deprecated
   aliases or command families.
3. The active clustering path has one engine, one persistence path, and one model
   policy; Review, Cluster, and Drift continue using it.
4. The standalone Cluster tab behaves as before retirement and remains available
   for future exploration work.
5. The operational snapshot row has one fixed representation, and the migration
   rejects rather than silently merging data from another configured source.
6. Configuration/source mismatch errors are concise, secret-safe, and traceback-free
   by default. The example environment cannot point mock mode at the documented API
   data directory.
7. Cleanup dry run lists only validated processed-artifact files, records all
   required checksums/measurements, and cannot address raw evidence or a broad root.
8. A clean data directory can sync, serve Review/Fleet Trends/Cluster/Drift, rebuild,
   doctor, and export without creating retired coordination files.
9. A disposable copy of the measured schema-v8 API store migrates to the same
   source-bound outcome while preserving 18,436 fixed facts and active model/event
   behavior. Schema-v9 compatibility is also covered.
10. Backup and restore rehearsal succeeds before a live cleanup approval is
    requested.
11. README and Grand Design describe FastAPI/web as primary and CLI as supporting
    administration.
12. Response-size budgets, sparse-data semantics, no-op synchronization behavior,
    and scheduler-ready catch-up remain satisfied after compatibility code removal.
13. Final code, memory, timing, response, file-count, and disk baselines are recorded
    against the pre-retirement measurements.

### Checkpoint B - separately approved live cleanup

1. The approved manifest and backup checksum match the artifacts presented at the
   destructive-action gate.
2. Confirmed cleanup removes only approved files/database structures and records
   completion or failure per target.
3. Post-cleanup integrity, row/value parity, web behavior, synchronization, doctor,
   export, and performance checks pass.
4. The backup and rollback instructions remain available outside the cleaned data
   directory.

## Reshaping Phase Definition of Done

The `0.6.x` phase is complete when:

- the web service reads one operational SQLite model;
- synchronization writes durable facts once;
- events survive normal retention;
- the browser receives compact server-scoped responses;
- one registered model pipeline serves Review, Cluster, and Drift;
- the CLI exposes only administration, repair, diagnosis, and export;
- legacy storage and code are removed through the approved recoverable process;
- source-bound configuration and startup failures are operator-friendly;
- current architecture, migration, rollback, and operations are documented and
  tested.

## Next Sprint Lead In
