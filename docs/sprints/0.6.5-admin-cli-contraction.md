# Sprint 0.6.5 - Admin CLI Contraction and Sustainment Sync

Status: implemented and verified on 2026-07-31.

## Problem Statement

The CLI currently exposes 25 commands across fetch, validation, raw lifecycle,
store loading, snapshot building, trend building, five workflow variants, reports,
legacy clustering, registered clustering, Maximo diagnostics, health, and serving.

That command tree reflects the order in which internal stages were developed. It is
not the operational interface required by a web-first service. Operators primarily
need to start the service, keep it synchronized through the last complete source
day, repair specific derived data, inspect health, and export data.

The original sprint outline required operators to provide every synchronization
date or range. That is insufficient for unattended sustainment: a task scheduler
should invoke one stable command, while the service determines what work remains
from durable state. Date planning belongs in the CLI even though installing or
configuring the scheduler does not.

This sprint contracts the public CLI while preserving internal functions and safe
recovery paths until final retirement.

## Working Decisions

### Public commands describe operator intent

The target command surface is:

```text
sensor-data serve
sensor-data sync
sensor-data rebuild
sensor-data doctor
sensor-data export
```

Internal stages remain testable Python functions. They are not all public Typer
commands.

### Source comes from service configuration

Normal commands use the configured source and data directory. Mock operation uses a
mock environment/configuration and separate data directory rather than parallel
`mock-*` command families.

### Synchronization is the normal update path

With no date arguments, `sync` catches the service up through the previous complete
calendar day in the configured source/facility timezone. For example, a run on July
31 targets data through July 30. It reads durable completion state, plans every
missing or incomplete date after the synchronization cursor, and processes dates in
chronological order.

An operator can still select one date or an inclusive range for controlled recovery,
testing, or historical loading. Each selected date performs the complete durable-fact
workflow:

```text
fetch -> validate -> persist -> verify -> active models -> finalize retention
```

It is idempotent and resumable from ingestion-run state. A date is advanced through
acquisition, validation, durable facts, verification, active models, and retention
stages without repeating verified stages unnecessarily. The synchronization cursor
moves only after the required stages are finalized. A model-deferred run records the
data as durable while leaving an explicit model-readiness gap for `doctor` and a
subsequent repair.

Normal synchronization never selects the current or a future source date. Explicit
date/range input beyond yesterday is rejected unless a deliberately separate test or
recovery policy is defined later.

### The scheduler does not calculate dates

The intended unattended invocation is stable:

```powershell
uv run sensor-data sync
```

Windows Task Scheduler, cron, or another supervisor only chooses when to invoke the
command and reacts to its exit status. It does not inspect SQLite, calculate
yesterday, maintain a separate last-run date, or build command-line ranges.

A fresh store needs an explicit or configured synchronization start date. Once
established, that boundary and the durable run state are authoritative. An already
current invocation is a successful no-op and must not rewrite facts, rebuild models,
or create retained artifacts.

### Synchronization is single-writer and bounded

Only one synchronization or rebuild writer may run at a time. A concurrent attempt
fails clearly without mutating state, and abandoned ownership can be diagnosed and
recovered safely.

Catch-up work is performed one date at a time so peak memory and temporary raw-data
usage do not grow with backlog length. Verified raw/native data follows the configured
retention policy after each date rather than accumulating until the entire range
finishes. An optional maximum-date limit may bound a scheduler run, but the result
must report that backlog remains and must not claim the service is current.

### Rebuild is the patch path

`rebuild` operates only on already acquired or explicitly re-fetched dates. It can
target snapshots, events, active models, or all derived facts. Destructive
replacement is explicit and audited.

### Export is opt-in

CSV/JSON files are generated only through `export`, with explicit domain, range,
scope, and destination arguments.

## Requirements

1. Implement the five target command families over the `0.6.1` services and `0.6.2`
   durable write path.
2. Make bare `sync` plan missing or incomplete work through yesterday in the
   configured source/facility timezone.
3. Make `sync` support an explicit date or inclusive bounded range for controlled
   operation and recovery.
4. Prevent normal automatic and explicit synchronization from selecting the current
   or a future source date.
5. Require an explicit/configured synchronization start date for a fresh store;
   persist enough state that the scheduler never owns a separate last-run date.
6. Make `sync` resume or safely retry incomplete ingestion-run stages without
   reacquiring or rebuilding stages that have already been verified.
7. Process catch-up dates chronologically and advance the durable synchronization
   cursor only after the required daily stages are finalized.
8. Build the active model by default after a snapshot succeeds, with an explicit
   option to defer models if needed.
9. Make an already-current `sync` a successful non-mutating no-op with a clear
   `current_through` result.
10. Prevent overlapping `sync`/`rebuild` writers with diagnosable, safely recoverable
   ownership state.
11. Bound catch-up memory and temporary disk usage by completing and applying
    retention one date at a time.
12. Make `rebuild` target `snapshots`, `events`, `models`, or `all`.
13. Require explicit source re-fetch permission when retained raw evidence is absent.
14. Make `doctor` report database schema, ingestion readiness, synchronization
    cursor/current-through status, snapshot/model gaps, stale models, event backfill
    gaps, configuration, and bounded Maximo connectivity diagnostics.
15. Make `export` write snapshot, trend, event, and active-model outputs without
   altering operational state.
16. Standardize human-readable output, exit behavior, and `--json` summaries across
    commands so unattended callers can distinguish current, advanced, partial, and
    failed outcomes.
17. Keep secrets out of logs and structured output.
18. Add deprecated aliases for necessary legacy commands during this sprint, with
    replacement instructions and no new behavior.
19. Stop registering report, raw lifecycle, store staging, trend build, mock
    workflow, and legacy clustering commands in the primary help tree.
20. Update CLI and operating documentation around web-first service administration,
    including the scheduler-safe invocation contract without installing a scheduler.

## Command Sketch

```powershell
uv run sensor-data serve
uv run sensor-data sync
uv run sensor-data sync --date 2026-07-30
uv run sensor-data sync --start-date 2026-07-24 --end-date 2026-07-30
uv run sensor-data rebuild --date 2026-07-30 --component models
uv run sensor-data doctor --start-date 2026-07-24 --end-date 2026-07-30
uv run sensor-data export trends --start-date 2026-07-24 --end-date 2026-07-30 --output exports/trends.csv
```

Exact option names may change, but separate mock/API workflow commands must not
return.

## In Scope

- Five-command public CLI.
- Scheduler-ready catch-up planning through the previous complete source day.
- Idempotent, resumable synchronization and targeted rebuild.
- Single-writer protection and machine-readable completion/exit behavior.
- Operational diagnosis.
- Explicit exports.
- Deprecation aliases and documentation.
- CLI test contraction around operator outcomes.

## Out of Scope

- Creating, registering, credentialing, or installing Task Scheduler, cron, Windows
  service, or other deployment jobs. The stable command those jobs invoke is in
  scope.
- Browser write/admin controls.
- Remote job queues.
- Multi-tenant source selection.
- Deleting internal functions required for compatibility.
- Removing legacy stored data.

## Compatibility Gate

Every documented operational outcome from the old CLI must map to one of:

- the new public commands;
- an internal test/helper API;
- an explicitly retired development artifact with no web dependency.

Before old commands are removed in `0.6.6`, run both old and new workflows against
temporary mock stores and compare durable facts.

## Acceptance Criteria

1. Top-level help presents five operator-oriented commands.
2. One `sync` command replaces the mock/API day/trend/range workflow matrix.
3. Bare `sync` on July 31 plans unfinished work through July 30 using the configured
   source timezone, without the caller supplying dates.
4. Normal automatic and explicit synchronization refuses July 31 or a future date in
   that example.
5. A fresh store refuses ambiguous unbounded synchronization and explains how to set
   its initial start date.
6. An already-current `sync` is a successful no-op that reports `current_through`
   without changing durable revisions or disk contents.
7. A failed catch-up resumes from its first unfinished stage/date without rebuilding
   verified dates, and the synchronization cursor never skips the failure.
8. Concurrent writer attempts do not overlap or mutate operational state.
9. `rebuild --component models` repairs a model gap without re-fetching sensor data.
10. `doctor` identifies current-through state and snapshot, event, and model gaps
    without mutating state.
11. `export` reproduces required CSV data without enabling routine artifact writes.
12. Deprecated commands clearly identify their replacement.
13. CLI documentation is materially shorter and centered on web-service operation.
14. Peak synchronization memory and temporary raw-data disk use remain approximately
    date-bounded rather than growing in proportion to a multi-day backlog.

## Next Sprint Lead In

Sprint `0.6.6` removes the compatibility scaffolding, archives or deletes redundant
artifacts through a recoverable cleanup process, and closes the reshaping phase with

date-planning `sensor-data sync` contract established here.

## Implementation Evidence

- The public help tree contains only `serve`, `sync`, `rebuild`, `doctor`, and
  `export`; compatibility families are hidden and emit replacement guidance.
- `sync` persists its start boundary, current-through cursor, per-date stage state,
  writer lease, and action audit in schema version 9.
- Bare synchronization plans through yesterday in the configured IANA timezone;
  explicit current/future dates are rejected.
- Daily work resumes from verified snapshots and ready models, applies retention per
  date, and does not advance its cursor past failure.
- `rebuild` targets snapshots, events, models, or all and requires explicit refetch
  permission when retained evidence is absent.
- `doctor` reports schema, cursor, snapshot/event/model gaps, stale models,
  incomplete runs, writer ownership, database bytes, and optional bounded Maximo
  connectivity.
- Snapshot, trend, event, and active-model exports write only to explicit
  destinations outside the operational data directory.
- The full suite passes with 165 tests, 1 skipped, and the existing Starlette/httpx
  deprecation warning.
- Timing, memory, temporary raw, retained raw, and SQLite growth figures are recorded
  in [the 0.6.5 benchmark](../benchmarks/0.6.5-admin-cli-contraction.md).
