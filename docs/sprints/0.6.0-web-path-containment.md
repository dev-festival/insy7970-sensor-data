# Sprint 0.6.0 - Web Path Containment

## Problem Statement

The browser is now the primary product surface, but its default read path still
materializes artifact-shaped payloads designed for CLI and report consumers.

On the current API dataset, a 22-day All Equipment Trend response is approximately
69 MB and the corresponding Snapshot Review response is approximately 112 MB.
Snapshot Review includes the same sensor trend rows twice, while SQLite, the API
composition layer, and the browser each perform their own filtering.

The live retention path has a more serious correctness problem. It fetches Waites
action items, stores them in a date-scoped table, and then deletes them with the
high-frequency observation staging rows. The ingestion ledger proves that the
source returned action items, but the web Events pane can no longer read them after
the normal release workflow.

This sprint contains the existing system before structural migration begins. It
improves the live web path immediately, establishes measurable response budgets,
and stops further durable-fact loss.

This sprint supersedes the earlier `0.5.0` lead-in that proposed user profiles,
caching, exports, and deployment hardening for `0.6.0`. Those features are deferred
until the operational data path is small and trustworthy.

## Working Decisions

### Web contracts take priority

The static browser and FastAPI service are released together. A response field that
exists only to preserve an oversized artifact-era browser contract may be removed
atomically from both sides.

Compatibility in this sprint means preserving user-visible behavior and API
semantics, not preserving duplicate collections or every historical response key.

### Response shapes match the question

- Chart responses contain only identifiers, dates, and the selected metric values
  needed to draw the chart.
- All Equipment and Asset Tree chart series are aggregated on the server.
- Detail tables are scoped and bounded separately from chart series.
- Snapshot Review must not return the same collection under multiple names.
- Missing values remain missing; containment must not introduce interpolation.

### Filtering has one owner

Scope, date range, metric, dimension, and statistic filters are applied by the
server query path. The browser renders the returned scope and does not repeat
business filtering over complete fleet collections.

### Action items are durable product facts

Waites action items are removed from the native-observation release set immediately.
High-frequency RMS, temperature, and ImpactVue staging rows may still be released
after snapshot verification. Compact events must survive.

### Readiness is explicit

Snapshot availability and registered-model availability are separate facts. The
bootstrap response must expose both so the browser does not treat a snapshot date as
implicitly cluster-ready.

## Requirements

1. Add repeatable measurements for the default API artifact discovery, equipment
   tree, Trend, and Snapshot Review requests using representative multi-day data.
2. Add response-size assertions for Trend and Snapshot Review.
3. Replace `SELECT *` trend reads with a projection containing only the requested
   metric fields and required identifiers.
4. Apply scope filtering at the SQLite query boundary, including sensor and
   equipment predicates.
5. Return server-aggregated chart series for All Equipment and Asset Tree scopes.
6. Bound detail rows with an explicit limit or pagination contract.
7. Remove the duplicate Snapshot Review `trend.rows` alias and update the browser
   to use one canonical collection.
8. Remove redundant browser scope filtering for already-scoped Trend responses.
9. Remove `waites_action_items` from the default native purge table set and prove
   that a normal release workflow preserves action items.
10. Expose per-date snapshot and registered-model readiness.
11. Select the latest snapshot-ready date for Snapshot data and clearly report
    missing model context without failing the remainder of the review.
12. Preserve Maximo's existing bounded activation rule and partial-provider error
    behavior.

## In Scope

- Trend and Snapshot Review query projection.
- Server-side scope filtering and aggregation.
- Response-size and timing characterization.
- Removal of duplicate response collections.
- Immediate action-item retention safeguard.
- Snapshot/model readiness metadata.
- Browser updates required by the compact response contract.

## Out of Scope

- Replacing the current SQLite snapshot schema.
- Removing CSV/JSON artifact writes.
- Deleting existing artifacts.
- Replacing either clustering implementation.
- Collapsing the CLI command tree.
- User profiles, authentication, scheduled jobs, or production deployment.
- Replacing the custom chart renderer.

## Compatibility Gate

Before this sprint is complete:

- every existing web view must still render from the current data directory;
- sparse-data coverage and Snapshot point selection must retain their `0.5.1`
  semantics;
- Waites events must remain after a release-mode test workflow;
- legacy artifact writers remain available for the next migration sprint.

No legacy file or table is deleted in `0.6.0`.

## Acceptance Criteria

1. The representative 22-day All Equipment Trend and Snapshot Review responses are
   each no larger than 2 MB of JSON.
2. A sensor-scoped request does not load or serialize unrelated fleet rows.
3. Snapshot Review contains no duplicate sensor collection.
4. All Equipment charts render the same aggregate meaning using server-produced
   series.
5. A release-mode ingestion containing Waites action items leaves durable,
   queryable event rows afterward.
6. A date with a snapshot but no registered model renders Snapshot, Trend, Events,
   and Measurements while reporting cluster context as unavailable.
7. Response budget tests fail if complete 74-field snapshot rows are accidentally
   reintroduced into trend chart responses.
